# Core Chain and Storage — Nethereum 7.1

A node built on Nethereum 7.1 prefetches state and computes its state root in parallel. On a 500-block mainnet replay it takes about 590–640 ms per block (about 36–40 Mgas/s), on an AMD Ryzen 9 3900X limited to 12 threads and 45 GB of memory, with the state on a consumer 1 TB NVMe SSD. This comes from one composition, `ExecutionStackFactory`, that gives every node role the same executor, state-root calculator and importer, warms each block on a `StatePrefetcher`, recovers senders and updates storage tries on worker threads, and reports per-block execution statistics. The importer now judges a block with the full header and body rule set, keeps blocks that do not extend the head as side blocks, and can make a heavier branch canonical, which is what the new `FollowerEngineApiService` needs to follow a consensus client. JSON-RPC gets one `IRpcDispatcher` seam, batch, subscription, filter and timeout limits, and the new `eth_baseFee` and `eth_getStorageValues`. `Nethereum.CoreChain.RocksDB` certifies the flat state against the healed trie at the end of a snap sync, wipes and frees snap state, reports a fatal store fault instead of stalling, exposes block-cache statistics, and runs freezer promotion and indexing as background jobs that wait for backfill and yield to execution. The freezer packages check a large index with sequential reads and are signed with the shared key.

## Where the time went

The 7.1 execution work was driven by replaying real mainnet blocks and following mainnet with a live node, and by removing each cost that grew with something other than the block's own work.

* A transaction snapshot copied every account and slot dirtied so far in the block, and the state overlay copied all of its maps, so a block of n transactions did n² work and each snapshot grew with the number of blocks waiting in the flush window. Both are now undo journals: a snapshot costs nothing to take and a revert undoes only what the transaction wrote
* Signature recovery, state reads and storage-trie updates ran on the single execution thread. Senders are now recovered for the whole block on dedicated threads, the block's transactions are pre-executed on a throwaway layer to load the state they touch, the trie paths of the keys the block writes are warmed before the root, and the dirty storage tries are updated in parallel when the root is computed (4 workers by default)
* A window-boundary flush built its whole write batch on the block path, and freezer promotion and indexing ran inside it, so a backlog of index work stalled execution for hours on a mainnet node. The batch is now staged inside the background flush, and promotion and indexing are background jobs that yield while the node is behind the tip
* A block that created and destroyed 796 contracts ran about five storage scans per account in its flush; an account that did not exist before the block now costs no storage scan when it is destroyed
* Contract code analysis is cached by code hash, a `STATICCALL`, `DELEGATECALL` or `CALLCODE` frame reads its target's code once per execution, and the secp256k1 contexts are built when the executor is composed instead of by the first block

## Security audit and conformance

The node's JSON-RPC, admin and block-production surfaces (three rounds, 28 findings) and the Engine API (6 findings) were audited before 7.1, and each finding was fixed with a test that fails before the fix.

* The highest-severity findings fixed: an unauthenticated caller could grow a default AppChain's memory without bound by sending requests with long, distinct method names (40 requests of 1 MB names held 117 MiB); one unfunded transaction calling a BLS or KZG precompile stopped a default AppChain from producing blocks for good; and a peer could make a forged header, state root included, the sync target of an Engine-API-driven follower
* The mainnet, DevChain and AppChain hosts each carried their own HTTP endpoint and the WebSocket handler parsed requests itself; there is now one envelope and one endpoint, with the batch, size, module, Host and Origin limits listed below
* The header and body rules are now the complete rule set, applied once at the import seam, each refusal naming its rule. The conformance runner passes every case it runs through the production import and execution paths on the 7.1 tree: 72,715 EEST blockchain tests, 61,813 EEST state tests, 38,881 ethereum/tests cases and 144,470 legacy Cancun and Constantinople cases

## Nethereum.CoreChain — Block execution and state root

Block execution waits on state reads, signature recovery and trie updates; 7.1 moves each onto its own threads and builds the stack the same way for every node.

* `ExecutionStackFactory.Build(IChainStoreBundle bundle, IChainActivations activations, Func<HardforkName, ChainConfig> chainConfigFactory, Func<HardforkName, HardforkConfig> hardforkConfigFactory, ExecutionStackOptions options)` returns an `ExecutionStack` (`Executor`, `Calculator`, `Importer`, `Prefetcher`, `Commit`, `SideChain`, `NewImporter()`). A follower, an AppChain producer and DevChain differ only in the `ExecutionStackOptions` they pass: `RewardPolicy` (required), `AuthorResolver`, `SealedByClique`, `FeeFreeBaseFee`, `SideChain` (`SideChainOptions`), `FlushCadence`, `PrefetchWorkers`, `StateRootWorkers`, `Prefetcher`, `TransactionVerifier`, `LoggerFactory`, `StateOverride` and `StateRootCalculatorFactory`. `ExecutionStackFactory.BuildExecutor` and `CreateImporter` build the pieces separately, `FlushCadences.ForBlocks(int blocks, string paramName = "blocks")` turns a configured interval into an `IFlushCadence` (`null` for 1, `FixedIntervalFlushCadence` above it, `ArgumentException` below it), and `BlockCommit` (`Arm`, `Clear`, `FlushAndJournalMatchedBlockAsync`, `DiscardAndRevertUnpersistedBlockAsync`, `DiscardCancelledBlockAsync`) is the commit sequence the importer and the producer share. The secp256k1 recovery and signing contexts are built when the executor is composed
* `StatePrefetcher(IStateStore state, IBlockStore blocks, IChainActivations activations, Func<HardforkName, ChainConfig> chainConfigFactory, Func<HardforkName, HardforkConfig> hardforkConfigFactory, Func<BlockHeader, string>? authorResolver, int workers, TimeSpan? shutdownBound = null)` runs a block's transactions on `state-prefetch-` worker threads against a throwaway layer, so the accounts, slots and code they touch are loaded before the serial executor reaches them and nothing is written to the store. `Begin(BlockHeader header, IList<ISignedTransaction> transactions)` returns a `PrefetchSession` (`Outcome` as `PrefetchOutcome`, `TriePathOutcome`, `StartTriePaths`, `Completed`) that `BlockExecutionOptions.Prefetch` carries to the executor. The session also warms the trie: each account or slot the real execution dirties has its trie path read on the prefetch threads, through a bounded queue (`PrefetchSession.TriePathQueueCapacity` 4096) that drops and counts keys instead of blocking, so the state root finds those nodes loaded. A block that cannot be planned, or a worker that throws, never fails the import and the roots and receipts equal those of a run with prefetch off. `ExecutionStackOptions.PrefetchWorkers` is 0 (off) by default; `Dispose()` joins the threads within `shutdownBound`, and rebuilding a stack does not accumulate threads
* Senders are recovered once per transaction on `sender-recovery-` worker threads at the start of a block, whether or not a prefetcher is present, and the executor reuses the recovered sender when it sees the same transaction instance; a transaction instance that was not the one recovered is recovered by the processor, and a sender that cannot be recovered refuses only that transaction as an invalid signature
* `IncrementalStateRootCalculator(IStateStore stateStore, ITrieNodeStore nodeStore = null, IHashProvider hashProvider = null, bool emitTombstones = false, int stateRootWorkers = 1)` updates the dirty storage tries of a block in parallel on `StateRootWorkers` dedicated threads (`ExecutionStackOptions.DefaultStateRootWorkers` 4 through the stack; `StateRootWorkers`, `WorkerThreadsStarted`, `Dispose()`). The threads start on the first incremental block and are not recreated, one worker starts none, the root equals the sequential root for any worker count, and a storage-trie update that throws fails the block instead of returning a partial root. `IIncrementalStateRootCalculator` gains the default members `NodeStore` and `BeginBlockTries(byte[] parentRoot)` (a `BlockTrieSet` that hands the prefetched tries to the root), and `IStateRootPhaseReporter.TakePhaseTimings()` returns `StateRootPhaseTimings`
* `BlockExecutionResult.Stats` and `BlockImporterResult.Stats` carry a `BlockExecutionStats` whenever the state store chain exposes `IStateReadMeterHost`: `AccountReads`, `StorageReads`, `CodeReads` with `AccountLoaded`, `StorageLoaded`, `CodeLoaded`, `CodeLoadBytes`; `AccountUpdates`, `AccountHashes`, `AccountCommits`, `StorageUpdates`, `StorageCommits` with the updated and deleted counts; `PrecompileCalls` (calls per precompile address, `PrecompileCallsKey`); `Execution` (which excludes state-read time), `Validation`, `DatabaseCommit`, `BlockWrite`, `TotalTime`, `MgasPerSecond`, `TransactionCount`, `GasUsed`. `BlockImporter` writes one `block.exec.stats` line per block from it, listing only the precompiles that were called; a chain without the read meter logs no line. 
* State stores keep a transaction's changes in an undo journal instead of copying every map, so taking and committing a transaction snapshot allocates the same over a window holding many buffered writes as over an empty one, and a revert restores the pre-transaction state, including a deleted-then-rewritten account's slots and clear mark. Dirty tracking survives a reverted snapshot for the keys dirtied before it. An account that was absent from the base state costs no storage scan when it is created and destroyed within the block (`IBaseAbsenceSource.WasAbsentInBase(EvmAddress address)`), while one present in the base is still wiped
* The state-store seams are byte-native: `IStateStore` gains default members for `EvmAddress` (`GetAccountAsync`, `SaveAccountAsync`, `AccountExistsAsync`, `DeleteAccountAsync`, `GetStorageAsync`, `SaveStorageAsync`, `SaveStorageByKeccakAsync`, `GetAllStorageAsync`, `ClearStorageAsync`, `GetDirtyStorageSlotsAsync`, `GetDirtyAccountsAsync`, `GetStorageClearedAccountsAsync`) that forward to the string forms, so existing implementers compile unchanged; `HistoricalStateStore` and `BufferedFlatStateStore` implement them natively and also `IStateReadMeterHost`, `IDirtyKeySource` (`TryAttachDirtyKeyObserver(IDirtyKeyObserver)`, `DetachDirtyKeyObserver`), `IAddressHashCache` and `IBaseAbsenceSource`. `StateKeys.AddressBytes` and `StorageSlotBytes` give the key bytes, and the state-root calculators, `ProofService` and `BlockAccessListRecorder` (now an `IAddressAccessRecorder`) read by address bytes. The strings and the `EvmAddress` forms of an account are the same account
* `StateStoreNodeDataService` implements `IAccountStorageAddressReader.AccountHasStorageAsync(EvmAddress address)`

## Nethereum.CoreChain — Block validity rules, side chains and reorgs

The importer now applies the complete header and body rule set before it executes a block, and keeps a branch it cannot yet execute.

* `HeaderValidator.Validate(BlockHeader header, BlockHeader parent, HardforkName fork, HardforkConfig config, SealRules seal, long? unixNow = null, bool daoExtraDataRequired = false, bool uncle = false, bool feeFreeBaseFee = false)` judges a header against its parent under `SealRules.ProofOfStake`, `Ethash` or `Clique`: extra-data size, nonce, uncle hash, timestamp, difficulty, gas limit and gas used, the gas-limit step bound, block number, base fee, withdrawals root, blob fields, block access list hash, slot number and, before the merge, the 15-second future-block limit and the ten-block DAO extra-data range. `BlockBodyValidator.ValidateAsync(header, transactions, uncles, withdrawals, fork, seal, unixNow)` checks the transactions root, the withdrawals root and the ommer rules (`MaximumUncles` 2, `AncestorWindow` 7). `EthashDifficulty.Calculate(HardforkName fork, ulong timestamp, BlockHeader parent)` is the pre-merge difficulty. `BlockValidationOptions` (`SealedByClique`, `FeeFreeBaseFee`, `UnixClock`, `UncleStore`, `TransactionVerifier`) is passed to `BlockExecutor`, which exposes `ValidateStructureAsync`, `Activations` and `StateRootCalculator`
* `BlockValidityCheck` and `IBlockValidityChecks` gain 18 verdicts, each with a wire identifier and a default `false` flag: `BlockRlpSize`, `UnknownParent`, `BlockNumber`, `Timestamp`, `FutureBlock`, `ExtraDataSize`, `DaoExtraData`, `GasLimitTooBig`, `Difficulty`, `Nonce`, `UnclesHash`, `Uncles`, `TransactionsRoot`, `WithdrawalsRootPresence`, `ParentBeaconRootPresence`, `BlockAccessListHashPresence`, `SlotNumberPresence` and `ParentNotHead`. From Osaka a block whose RLP exceeds 8,388,608 bytes is `BlockRlpSize`. A refused block names its failing rule in `BlockImporterResult.FailedChecks` and persists nothing, and a block whose parent is unknown is a gap (`UnknownParent`), not an invalid block
* `BlockImporter` built with `SideChainSupport` (`ExecutionStackOptions.SideChain`) stores a block that does not extend the head as a side block (`BlockImportDisposition.StoredAsSide`, `AlreadySide`, `AlreadyCanonical`, `Refused`, `UnknownParent`, `ExtendedCanonical`), `SetCanonicalAsync(byte[] blockHash, CancellationToken ct = default)` rewinds to the common ancestor and replays the branch (`SetCanonicalResult` with a `ChainReorganisation` and the dropped transactions; `SetCanonicalStatus.NoOp`, `Reorganised`, `BranchInvalid`, `AncestryUnavailable`, `RewindUnavailable`, `TooDeepReorg`), and an invalid branch is remembered (`TryGetInvalidBlock(byte[] blockHash, out byte[]? latestValidHash)`). `ISideBlockStore` (`Put`, `TryGet`, `Contains`, `Remove`, `PruneBelow`), `InMemorySideBlockStore`, `CanonicalOrSideBlockStore`, `SideChainSupport.MaxReorgDepth` (default `DefaultMaxReorgDepth` 64), `SideChainOptions.AdoptByDifficulty` (`DifficultyForkChoice`; a zero-difficulty branch is adopted when it arrives) and `BlockImporter.PruneSideBlocksBelow(ulong blockNumber)` complete it. A refused block leaves no state behind, including a cleared storage slot, so the next valid block imports
* `IRewindCoordinator.RewindToAsync(ulong targetBlock, RewindPolicy policy, RewindScope scope, CancellationToken ct = default)` takes `RewindScope.ExecutionAndChain` or `ExecutionOnly`. Every executed block records the hash it executed (`IChainMetadataStore.SaveExecutedHash` and `GetExecutedHash`, `ExecutedHashRetention.Blocks` 1,024), so the tip path finds the common ancestor from that record, also after a restart, and `BlockImporter` and `ConsensusGatedBlockExecutor` rewind through one shared primitive. `IMempoolReorgReconciler.ReconcileAsync` receives the orphaned and winning branch transactions, and the pool rebuilds its pending nonces from the transactions still pending after a partial block
* `FollowerOptions.ChainWriteGate` (an `AsyncGate`: `WaitAsync`, `Release`, `Publish`, `SetHead`, `HeadNumber`, `HeadHash`) is the per-block write gate shared with the Engine API, so one writer executes at a time and a follower that reaches a block another writer executed skips it; `FollowerOptions.AfterRewindAsync` lets the host drop warm state after a rewind. A follower hands a competing block to the importer and backs off from a stream that keeps handing it blocks ahead of its head instead of restarting hot

## Nethereum.CoreChain — Engine API follower

* `FollowerEngineApiService(IChainStoreBundle bundle, AsyncGate gate, ChainConfig config, FollowerOptions options, EnginePayloadStash stash, EngineHeaderResolver resolver, IEngineForkchoiceSink sink, ILogger logger = null)` is an `IEngineApiService` that takes `newPayload` and `forkchoiceUpdated` from a consensus client and drives the importer the sync loop uses, under the same write gate. A payload that extends the head is imported once and answered `VALID`, also before the first `forkchoiceUpdated`; a payload whose parent is known but is not the head is `ACCEPTED` and stashed; an unknown parent is `SYNCING` and the devp2p sync is pointed at the forkchoice head. A wrong state root or a timestamp not after the parent's is `INVALID` with the parent as `latestValidHash`, a wrong declared hash is `INVALID_BLOCK_HASH`, its descendants stay `INVALID`, and a transaction that does not decode is `INVALID` instead of an internal error
* `forkchoiceUpdated` to a sibling head runs the reorg path, to the current head is a no-op, to a head beyond `MaxReorgDepth` answers `-38006` and leaves the head, and to a head that no store, stash or peer holds is `SYNCING`; the follower drops stashed payloads below the finalized block. `EngineHeaderResolver` uses a header fetched from peers only when it hashes to the requested hash, so a peer cannot publish a forged header as the sync target. `newPayloadV3` to `V5` compare `expectedBlobVersionedHashes` with the payload's blob transactions in order and answer `INVALID` on a mismatch (`EnginePayloadDecoder.CheckBlobVersionedHashes`). `SetHeadAsync(ulong target)` rewinds through the same path
* `EnginePayloadStash(EnginePayloadStashOptions options)` keeps at most `MaxBlocks` (`DefaultMaxBlocks` 128) blocks and `MaxBytes` (`DefaultMaxBytes` 256 MiB) of retained transaction data, evicts the oldest first, always keeps the newest, and reports `RetainedBytes`; the 7.0 stash was bounded by count alone. `EnginePayloadDecoder` (`Decode`, `DecodeTransactions`, `DecodeDeclaredBlockAccessList`, `RequestsHashFor`, `ToModelWithdrawals`), `DecodedEnginePayload`, `InvalidEnginePayloadException` and `EngineForkchoiceHead` carry the payload mapping

## Nethereum.CoreChain — Block production and transaction admission

* `BlockProducer` isolates a transaction that faults the host: it is reported in `BlockProductionResult.DroppedTransactions` (`DroppedTransaction.Transaction`, `Reason`), the same sender's later transactions are returned in `DeferredTransactions`, and the block is produced again from the rest; after four drops in a block the fifth cuts the block to the transactions before it. The retry runs only when the executed prefix can be reverted (an atomic commit or the `HistoricalStateStore` journal); over a bare store the block fails as before. A transaction that did not fit the gas or blob budget left in the block is deferred only if it would fit an empty block, and dropped otherwise. `ITransactionOrderingPolicy.Order(pool, blockContext, ct)` no longer takes a gas limit: the executor's fit check against the gas left after actual use decides. From Osaka the producer stops adding transactions before the block would reach the EIP-7934 limit and the cut transactions stay pending.
* `TransactionAdmissionRules(BigInteger chainId, long maxGasLimit, int maxTransactionSizeBytes = DefaultMaxTransactionSizeBytes, int maxBlobTransactionSizeBytes = DefaultMaxBlobTransactionSizeBytes)` is the one admission rule JSON-RPC submission and peer relay share: `FirstRefusal(ISignedTransaction tx)` returns the first of `BlobCountReason`, `OversizeReason`, `InvalidSignatureReason`, `WrongChainIdReason`, `GasLimitTooHighReason` and `FeeCapBelowPriorityFeeReason`. A blob transaction must carry between one and `MAX_BLOBS_PER_TX` blobs and is measured with its sidecar against `DefaultMaxBlobTransactionSizeBytes` (1 MiB, up from 917,504 bytes); every other type is capped at `DefaultMaxTransactionSizeBytes` (128 KiB)
* `ChainConfig.FeeFreeBaseFee` (virtual, `false`) and `BlockProductionOptions.FeeFreeBaseFee` keep the base fee at zero on a chain that declares it, in production, header validation, `eth_baseFee` and `eth_feeHistory`, so one half-full block can no longer move the next base fee off zero. `GasLimitBound.StepToward(long parentGasLimit, long desiredGasLimit)` lets a producer step its gas limit toward a target within the parent bound. A pre-London block executes with no base fee whatever base fee the chain is configured with

## Nethereum.CoreChain — JSON-RPC

* `IRpcDispatcher` (`DispatchAsync`, `DispatchBatchAsync`, `MaxBatchSize`) is the seam every front end dispatches through; `RpcDispatcher` and `InstrumentedRpcDispatcher` implement it, `WebSocketRpcHandler(SubscriptionManager subscriptionManager, IRpcDispatcher dispatcher, JsonSerializerOptions serializerOptions = null)` takes it, and `JsonRpcEnvelope` is the front end the HTTP hosts share. A batch above `RpcDispatcher.DefaultMaxBatchSize` (1,000) is answered with one `BatchTooLarge` error carrying the id of the first call, before the members are parsed (`RpcBatchGuard.RejectOversizedBatch`); a notification gets no response; a batch member that is not a request object gets `-32600` while the others are answered; a batch response is capped at `JsonRpcEnvelope.DefaultMaxResponseSize` (25,000,000 bytes) and the members that no longer fit answer `ResponseTooLargeCode`
* `RpcModuleSet.Parse("eth,net,web3")` (`DefaultModules`; `txpool`, `debug` and `admin` are opt-in, an unknown name throws `ArgumentException`) with `AddStandardHandlers(RpcModuleSet)` registers only the namespaces a node lists. `eth_baseFee` (`EthBaseFeeHandler`) answers the base fee the next block must carry, and `eth_getStorageValues` (`EthGetStorageValuesHandler`) answers up to 1,024 slots in one call as 32-byte words, with `-32602` for an empty request or a key longer than 32 bytes and `-38026` above the limit
* Input and errors: invalid parameters are `-32602` and never `-32603` (`RpcJsonElementExtensions.RequireRpcString`, `GetOptionalRpcString`, `RequireRpcObject`, `GetRpcString`; a lone UTF-16 surrogate is refused), `-32603` is always the plain `Internal error`, `HistoricalStateNotAvailableException` answers `-32000` with its message, an unknown method is metered under the one key `InstrumentedRpcDispatcher.UnknownMethodMetric` and its name is truncated in the error text, and the log lines an unauthenticated caller can trigger are written at Debug
* Limits: `eth_call`, `eth_estimateGas`, `eth_createAccessList` and `eth_simulateV1` run under `ChainConfig.RpcEvmTimeout` and the `debug_trace*` methods under `ChainConfig.RpcTraceTimeout` (5 seconds each), the whole `eth_estimateGas` search sharing one deadline; `eth_getLogs`, `eth_newFilter` and `eth_subscribe("logs")` refuse more than 4 topic positions or more than `ChainConfig.RpcLogQueryLimit` (1,000) addresses or values in a position with `-32602`; `eth_newFilter` starts at the head and a poll returns only logs since the last poll under the `getLogs` caps, with random 128-bit filter ids (`FilterIdGenerator`); `eth_feeHistory` takes at most 100 strictly ascending percentiles
* Subscriptions: a WebSocket message is read to its end under `WebSocketRpcHandler.MaxMessageSize` (32 MiB), each connection has an outbox with a `WriteTimeout` of 10 seconds so a slow subscriber cannot stall a broadcast, `SubscriptionManager.MaxSubscriptionsPerConnection` caps a connection at 200, `SubscriptionBroadcaster` hands blocks from the producer to the fan-out through a queue of `QueuedBlocks` (128) that drops the oldest, and `WebSocketRpcHandler.SubscriptionsEnabled` follows the `eth` module

## Nethereum.CoreChain — Proofs and genesis

* `BlockHashesTree.VerifyProof(root, blockHash, index, proof, totalLeaves)` rejects a proof for an index that is out of range, negative or another valid index, a proof whose length is not a multiple of 32, a null proof or hash, a truncated or extended proof and a misreported `totalLeaves`, without throwing
* `StandardGenesisLoader.Parse` reads the `blobSchedule` and `bpoNTime` entries into the fork schedule (`StandardGenesisForkConfig.BpoTimes`; a `bpoN` entry without its time is left out), and `DeclaresAnySystemContract(StandardGenesisDocument document)` says whether the allocation already holds a system contract. `GenesisInitializer.EnsureAsync(IChainStoreBundle bundle, StandardGenesisDocument document, ChainConfig chain)` writes the allocation, the fork's predeploys unless the genesis declares system contracts, the state root and block 0 on the first start, and on a store that already holds a genesis verifies the stored hash and throws `InvalidOperationException` when a different genesis is configured. `GenesisHeaderBuilder.Build(ChainConfig config, HardforkName fork, byte[] stateRoot)` builds the genesis header

## Nethereum.CoreChain.RocksDB — Snap state, store faults and the freezer

* `IFlatStateReconciler` certifies the flat account and storage state against the healed trie root in one run at the end of a snap sync, and `RocksDbChainStoreBundle.VerifyFlatStateAsync(byte[] stateRoot, Action<string> progress, CancellationToken ct, long sampleAccountsPerShard = 0)` runs the same walk without writing. Worker threads drain 256 account units; a unit hashes its flat rows and compares the result with the trie's node reference, so a matching unit costs one hash, and a storage owner with many slots is proven as sixteen first-nibble ranges. Only a range that differs is walked leaf by leaf: ghost rows are deleted, diverged rows patched, a missing account added, orphan storage rows deleted, and an undecodable account row sends its unit to the leaf walk. A trie node missing under a diverged range is never regenerated by the certify pass: it is reported as `FlatReconcileUnresolvableNodeException` with the owner and path in `MissingNodes`, nothing is written for that range, and the heal deletes the ancestor chain of the hole and fetches it again. The reconciler refuses to run while a node-commit block context holds a current block
* The progress of a generation is kept in its own column family (`RocksDbManager.CF_FLAT_GENERATION`), so a cancelled or crashed run resumes with only its unfinished units hashed, and a heal toward a newer root re-walks only the regions it changed; `PathHealNodeSink` (now an `ISnapFlatStateWriter`) captures the first pre-image of every node it overwrites or deletes and drops its own flat writes while a generation runs, `IHealNodeSink.DeleteNode(bool isStorage, byte[] accountHash, byte[] nibblePath)` deletes a node at its path, and `IFlatStateReconciler.DiscardCertifyJournal()` removes the journal
* `RocksDbChainStoreBundle.ResetSnapBootstrapStateAsync(Action<string> progress, CancellationToken ct)` (`ISnapBootstrapStateReset`) reports each wiped column family, the compaction and the completion; the SST files of a wiped column family are gone before the database closes, chain metadata is left intact, the checkpoints of the state it wipes are deleted (as `ResetStateOnlyAsync` also does) and the metadata column family is left with no delete tombstones. A rewind that moves the head below a checkpoint deletes that checkpoint too
* `IStoreFaultSource.FatalStoreFault` on the bundle is `null` while the databases accept writes and a message once one cannot: a RocksDB background error that stops writes (found by `RocksDbWritePressureMonitor.FatalBackgroundError()` even with no write in flight), or a corrupted file a compaction or write surfaces. A recovered background error and ordinary retryable pressure are not faults, so the host can exit on a fault instead of stalling
* `RocksDbManager.ReadCacheStats()` returns `RocksDbCacheStats` (`IndexHit`, `IndexMiss`, `FilterHit`, `FilterMiss`, `DataHit`, `DataMiss`, `BytesRead`, `UsageBytes`; `Parse(string statisticsString, string blockCacheUsage)`) when `RocksDbStorageOptions.EnableStatistics` is on and throws `InvalidOperationException` when it is off (`StatisticsEnabled`)
* Freezer promotion and indexing are background jobs, not part of the block flush: the follower run starts them (`FreezerBackgroundIndexer` for the indexes), a boundary flush returns without freezing or indexing, and disposing the bundle stops them in order before any store closes. `FreezerPromotionService` waits while the next block to freeze is below `IHotBlockWindowSource.HotFloorNumber` (`RocksDbHotBlockWindowStore.TryGetOldestNumber()`), so a snap-synced node whose earlier blocks arrive through history backfill no longer fails every round and resumes contiguously once they are frozen. After `SetYieldToExecution(true)` the jobs and the history backfill pause while the executed head is more than 32 blocks behind the trusted tip and resume when it is within 2 (`IBackfillPauseControl.ShouldYieldToExecution()`, `DescribeYieldToExecution()`); blocks that age past the threshold meanwhile stay readable by number and by hash. `IAtomicBlockFlush.DescribeLastFlush()` names the stage a flush awaited and the previous write
* `BootRecoveryGate.HasPendingRestore(string dataDir)` says whether a checkpoint restore is waiting, so a write-free check can refuse a store that still needs recovery
* `RocksDbStorageOptions.BackgroundFreezeIndexing` is `true` by default (`false` leaves frozen blocks unindexed while freezing still advances), and `BlobBaseFeeFraction` (`IBlobBaseFeeFractionResolver`, default `ChainBlobBaseFeeFractionResolver.Mainnet`) selects the blob base-fee fraction used to re-derive frozen blob receipts. The composite block, transaction, receipt, uncle, withdrawal and block-access-list stores answer from the hot window only when it holds the block's body, and a rewind removes the transaction lookups of the blocks it drops (`ITransactionStore.DeleteLookupsByBlockNumberAsync(BigInteger blockNumber)`). A background flush in flight refuses an unarmed trie commit or range delete instead of writing under it, and a prefetcher resolving a node rewritten earlier in the flush window reads the window's version, not the disk's

## Nethereum.CoreChain.Freezer and Nethereum.Freezer

* `ChainBlobBaseFeeFractionResolver(IChainActivations activations, Func<HardforkName, HardforkConfig> configForFork)` (`FractionForBlock(BlockHeader header)`, `Mainnet`) reads the blob base-fee update fraction from the fork schedule active at the header's block and timestamp, so a receipt frozen across a blob-parameter change derives the right blob gas price
* `IHotBlockWindowSource.HotFloorNumber` is the oldest block the hot window holds; `FreezerPromotionService.PromoteFinalizedBlocks` returns nothing promoted while the freezer head is below it
* `IFreezerIndex.FirstItemBreakingSequence()` (a default member, implemented by `FreezerIndex`) reads the index in 1 MiB chunks and returns the first item whose entry does not follow its predecessor, or `null`; opening a table uses it for the self-consistency check, so the cost is proportional to the index size in megabytes rather than to its entries. `ReadOnly` throws `FreezerValidationException` at the defect and `Append` truncates the index to the item before it

## Bug Fixes

* A block cancelled by host shutdown in the middle of a flush window was reverted, which the window cannot support; it is abandoned and the follower resumes from its durable cursor
* A cleared storage slot came back after a block was refused or rewound; the state stores restore it, and a refused block leaves no state behind
* The pool's pending nonces were cleared after a block that included only some of an account's transactions; they are rebuilt from the transactions still pending
* A storage trie with a missing inner node produced a state root; it throws instead of returning a root
* A pre-London block took the chain's configured base fee into its execution context; it executes with none
* A set-then-cleared storage slot within one block left the wrong storage root in the intermediate state
* `BlockHashesTree.VerifyProof` accepted a proof at another position when `totalLeaves` was misreported; the leaf count must come from the trusted anchor
* A forged header fetched from a peer could become the sync target of an Engine-driven follower; a header is used only when it hashes to the requested hash
* `newPayloadV3` to `V5` ignored `expectedBlobVersionedHashes`, and a payload with an undecodable transaction was answered with an internal error
* The `newPayload` stash held 1,024 blocks whatever their size (about 1 GiB for 256 KiB of transactions each); it is bounded by `MaxBlocks` and `MaxBytes`
* An unregistered method name was kept in the metrics for every distinct name, so a caller could grow the node's memory without bound; they share one key
* One filter naming tens of thousands of addresses or topics, one connection holding tens of thousands of subscriptions, and a subscriber that never reads could each stall or exhaust a node; the width, subscription and outbox limits above close them
* `eth_call`, `eth_estimateGas` and `eth_createAccessList` could run an endless loop without limit; they abort at `RpcEvmTimeout`
* A honest six-blob transaction with more than about 90 KB of call data was refused by the 917,504-byte limit, a blob transaction in the network form was refused against the 128 KiB cap, and a blob transaction with more blobs than any block can hold could be pooled; the shared admission rule fixes all three
* On a snap-synced follower freezer promotion threw every round because the hot window never holds block 1; it waits for backfill
* A RocksDB background error left a node stalled for hours without a message; `FatalStoreFault` reports it
* Wiping snap state left its SST files on disk until the database closed, left stale checkpoints and left delete tombstones in the metadata column family
* A composite store served a block's transactions and receipts from the hot window when the window held only its header
* A rewind below a saved checkpoint left that checkpoint in place
* A fee-free chain whose block was more than half full moved the next base fee to 1, after which zero-price transactions were refused
* A RocksDB compaction that failed its checksum made every write throw while nothing exited: a mainnet node sat at 50.2% of Phase 2 for 6 hours 18 minutes. A write failure that is not transient now stops the node with exit code 1
* On a snap-synced follower freezer promotion failed every round (about 7,300 failed rounds on one mainnet run) because it started at block 1, which the hot window never holds
* The tip path, `SetCanonical` and the follower each had their own rewind; three divergent rewind paths are replaced by one rewind-to-ancestor primitive that finds the common ancestor from the persisted executed hash, also after a restart
* A node-history rewind left the reverse-diff rows of the blocks it rolled back in place
* Disposing the RocksDB manager disposed a lock that late callers were still queued on, so shutdown raised `SynchronizationLockException` instead of `ObjectDisposedException`
* A block that broke a header or body rule (extra data, timestamp, difficulty, nonce, gas-limit step, uncles, transactions or withdrawals root) was executed and then refused only by its state root, or not refused at all

## Breaking Changes

* Removed: `TrieFallbackStateStore` and `StoresFactory.SnapSync(IStateStore, INodeBlobStore, Func<byte[]>, bool)`. Production never constructed them; snapped state resolves directly through `IChainStoreBundle.State`
* Signature: `ITransactionOrderingPolicy.Order` and `MempoolNonceOrderingPolicy.Order` lost their `BigInteger gasLimit` parameter; an implementer drops the parameter and relies on the executor's fit check. `MempoolNonceOrderingPolicy.Instance` is now built over the default verifier, and `new MempoolNonceOrderingPolicy()` no longer compiles: the only constructor takes `ITransactionVerificationAndRecovery? verifier`, so a 7.0 caller passes `null` or uses `Instance`
* Signature: `IPendingFlushFlatOverlay.TryGetAccount` and `TryGetStorage` take an `EvmAddress` instead of a `string`
* Added member: `IHotBlockWindowSource.HotFloorNumber` is a required member of the interface; an external implementer adds it (the oldest block its hot window holds)
* Signature (source compatible, recompile a 7.0 caller): `BlockExecutor` and `BlockImporter` constructors gained overloads taking `BlockValidationOptions`, `SideChainSupport` and `BlockCommit`, and the second `BlockProducer` constructor gained a trailing `BlockCommit? commit = null`; `IncrementalStateRootCalculator(…, bool emitTombstones = false, int stateRootWorkers = 1)`; `EnginePayloadBuild` and `FlatReconcileUnresolvableNodeException` gained constructors taking withdrawals and missing nodes; `CapturingJournalingPathNodeStore` takes an optional `BackgroundFlushSignal`; `WebSocketRpcHandler`, `PathHealNodeSink`, `RocksDbWritePressureMonitor` and `SyncBulkSaveService` constructors chain to new ones; `RocksDbChainStoreBundle` and `PathHealNodeSink` implement more interfaces (`ISnapBootstrapStateReset`, `IStoreFaultSource`, `ISnapFlatStateWriter`)
* Changed: `FreezerBulkIndexBuilder.FilterMapsChunkTargetBytes` is 32 MiB (was 250 MiB), so a decoded filter-maps chunk is about 1 GB rather than 8 GB; it is a constant, so recompile a caller that read it
* Obsolete, not removed: the deferred storage debt API (`DeferredStorageDebt`, `StorageCompleteness`, `DeferredStorageReason`, `DeferredStorageDebtCodec`, `IChainMetadataStore.UpsertDeferredStorageDebt`, `ListOpenDeferredStorageDebts`, `CountOpenDeferredStorageDebts`, `ClearDeferredStorageDebt`, `ClearAllDeferredStorageDebts`, `IBundleBatch.UpsertDeferredStorageDebt`) because snap sync no longer records debt, `FreezerBackgroundIndexer.IndexFrozenInline` because frozen blocks are indexed by the background trailer only, and `RocksDbTrieNodeStore.DeleteRange(byte[] owner)`, which forwards to `RocksDbPathTrieNodeStore.DeleteRange`
* Behaviour: the importer refuses blocks the 7.0 importer accepted when they break a header or body rule above (extra data over 32 bytes, a timestamp not after the parent's, a wrong difficulty or nonce, a transactions root that does not match, a block over the Osaka size limit); a block that does not extend the head is refused as `ParentNotHead` unless the stack has `SideChainSupport`
* Behaviour: `RocksDbStorageOptions.BackgroundFreezeIndexing` is `true` (was `false`), so frozen blocks are not readable by hash, transaction, receipt or log until the trailer reaches them; set it to `false` to keep the 7.0 value. The blob transaction size limit is 1 MiB for type 3 and 128 KiB for the rest, RPC and peer admission refuse a blob count outside 1 to `MAX_BLOBS_PER_TX`, and the `newPayload` stash defaults to 128 blocks and 256 MiB
* Behaviour: JSON-RPC refuses a batch above 1,000 requests, a log filter wider than 4 topic positions or 1,000 values, and a subscription beyond 200 per connection; `eth_call`, `eth_estimateGas`, `eth_createAccessList`, `eth_simulateV1` and the trace methods abort after 5 seconds

## Build & Packaging

* `Nethereum.CoreChain.RocksDB`, `Nethereum.CoreChain.Freezer` and `Nethereum.Freezer` are signed with the shared key (the published 7.0 tree had them unsigned, and the `Nethereum.CoreChain.RocksDB` README said so); they take `<Version>` from `$(NethereumVersion)` and ship stable
* READMEs: `Nethereum.CoreChain` gains the execution stack, state prefetch and parallel state root, execution statistics, transaction admission, header and body rules, side chains and reorgs, Engine API follower and JSON-RPC sections, its `FollowerOptions.ChainWriteGate` is an `AsyncGate`, and its block production block gains `FeeFreeBaseFee`, `DeferredTransactions` and `DroppedTransactions`; `Nethereum.CoreChain.RocksDB` gains the store fault, cache statistics, snap bootstrap state and flat-state certification sections, the freezer job text, `BlobBaseFeeFraction`, and is no longer described as unsigned; `Nethereum.CoreChain.Freezer` gains `HotFloorNumber` and `ChainBlobBaseFeeFractionResolver`; `Nethereum.Freezer` gains `FirstItemBreakingSequence`. The dependency lists no longer name `Nethereum.Documentation`, and the four READMEs describe the freezer format without naming another client
