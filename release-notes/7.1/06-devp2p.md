# DevP2P — Nethereum 7.1

Nethereum 7.1 ships `Nethereum.DevP2P` and `Nethereum.DevP2P.Sync` as stable packages that can sync a node from untrusted peers. A node cold-starts from `snap/1` state or, behind the Amsterdam fork, from the `snap/2` flat-state download with block-access-list catch-up; it then follows the chain head by pulling the blocks that peers announce with `BlockRangeUpdate`, and relays and serves transactions, blocks, receipts and state to its own peers. Peering is bounded at every layer: pending handshakes, per-IP and per-subnet caps, per-frame read and write deadlines, a 10 MiB cap on `eth` and `snap` messages, responses that are checked against their request before they are decoded, strict canonical RLP on the wire, and one budget for the bytes being decoded across all connections. Peers are held to account: an empty reply earns no credit, a header reply that does not chain is a protocol violation, a Status for another network, genesis or fork is refused, and a forged head announcement cannot make a follower download the chain again. Discovery verifies what it accepts: discv5 NODES replies and DNS ENR trees are signature-checked, discv4 bonding is capped and revalidated, both routing tables limit nodes per subnet, and the per-IP discv5 packet filter is opt-in. Snap sync heals mismatched storage at the live pivot instead of recording deferred debt, remembers which peers cannot serve a root, waits for a snap peer instead of recycling, and certifies the flat state against the root the heal converged to.

## Security audit and verification

`Nethereum.DevP2P` was a preview in 7.0. Before it ships as stable, every surface a remote peer can reach went through a findings-driven security audit: the RLPx transport and peer-message handling (nine rounds), discovery (four rounds), the sync engine, and the Engine API that drives a follower. Every finding was fixed with a test that fails before the fix and passes after it. The changes below are the result.

* The highest-severity findings fixed: a frame of nested RLP lists overflowed the stack and killed the process; a `Transactions` message of 10-byte transactions allocated 64 times its payload with no count bound; list-valued ENR entries were re-encoded as byte strings, so every real execution-layer record failed signature verification and the mainnet DNS tree resolved no nodes; discv5 accepted unsigned and unsolicited NODES records; one peer answering every body request with nothing stalled a follower in a hot loop; one peer announcing a far head and answering empty stalled every follower at the tip; and a peer could hand an Engine-API-driven follower a forged header, state root included, as its sync target
* Peer-message decoding is checked in CI against a pinned reference decoder: 200,000 inputs (real corpora, generated objects and structural mutants: leading zeros, widths off by one, list and string swaps, dropped, duplicated and trailing elements, integer boundaries, every type byte) must be accepted or refused by both, and accepted inputs must re-encode, hash and recover the sender identically. Eight disagreements were found and fixed; the run ends with 81,324 agreed accepts, 117,884 agreed refusals and no disagreement
* The streaming decoders were checked against the previous decoders on 351,283 real mainnet block RLPs plus generated receipts, block access lists and snap responses, with no mismatch
* The reference `devp2p` conformance suites pass against a Nethereum node: `eth`, `snap`, discv4 (15 of 15 subtests) and discv5

## Nethereum.DevP2P — RLPx transport limits and back-pressure

Every message is bounded before it is decoded, on both read paths.

* `RlpxConnection.MaxSubProtocolMessageSize` (10 * 1024 * 1024 bytes): an `eth` or `snap` message whose payload is larger is refused with `DisconnectReason.ProtocolBreach` before any decode, in the request-id dispatcher loop and in the pull-based `ReceiveMessageAsync` / `ReceiveStatusAsync`. A message id outside every negotiated capability is a `ProtocolBreach` on both paths, before it counts as liveness. Payloads of other capabilities are bound by the frame size only
* Frames: `RlpxFrameReader.MaxFrameSize` (16 MiB - 1) bounds a Snappy-decoded frame (`MaxDecompressedFrameSize` is now the same limit, was 32 MiB); `RlpxFrameReader.BaseProtocolMaxMsgSize` (2048) bounds base-protocol messages, and a frame larger than that plus 16 bytes is refused until the Hello is complete; a zero-size frame raises `CryptographicException`. The Hello must carry the 64-byte node id the handshake authenticated (`NullIdentity` / `UnexpectedIdentity` otherwise), at most 64 capabilities and a client id of at most 256 characters
* `RlpxResponseBound` (`Items(long maxItems)`, `ContentBytes(long maxBytes)`, `Unbounded`, `Kind`, `Limit`) and `RlpxResponseBoundKind`; `RlpxConnection.SendRequestAsync(sendMsgId, payload, expectedResponseMsgId, requestId, timeout, bound, ct)` and a generic overload that also takes a `Func<byte[], T> decode`. The dispatcher checks each response before decoding it: an unknown request id, a message id other than the one the request expects, a malformed envelope, or more items (or content bytes) than the bound fails the request and disconnects the peer with `ProtocolBreach`. A late response to a timed-out request is dropped quietly for `DevP2PConfig.AbandonedRequestTrackingMs` (300000)
* `RlpxResponseCodes.IsResponse(string capabilityName, int relativeMessageId)` is the table of which `eth` and `snap` message ids are responses
* Strict canonical RLP: response envelopes, and the wire messages that `Nethereum.Model.P2P` decodes, are read with `Nethereum.RLP.RlpReader`. It refuses a single byte below `0x80` carrying a string prefix, a length-of-length with a leading zero, a long form used for a payload under 56 bytes, an integer with a leading zero or wider than 64 bits, nesting deeper than `RLP.MaxDecodeDepth` (64), and bytes after the top-level value; a malformed response envelope is a `ProtocolBreach`
* `InFlightDecodeLimiter` (`AcquireAsync(long bytes, CancellationToken ct)` returns an `InFlightDecodeLease`; `CapacityBytes`, `InFlightBytes`, `ForMaxPeers(int)`, `Shared`, `DefaultMaxPeers` = 25, `BytesPerPeer` = 4 MiB) is one budget for the bytes being decoded across the connections that share it. Waiters are admitted in arrival order, an oversize request is admitted when nothing else is in flight, and the read loop waits for a lease instead of buffering. `DevP2PConfig.DecodeLimiter` selects it (the 100 MiB `Shared` limiter when `null`); `RlpxConnection.AcquireDecodeLeaseAsync(int payloadBytes, CancellationToken ct)` leases for a serving loop
* `RlpxPeerSlots(int maxPeers)` with `TryAcquire(bool trusted)`, `Release()` and `Active`: `RlpxListener` claims its `MaxPeers` slots through it, so concurrent handshakes cannot overshoot; a trusted peer is never refused and an unbalanced `Release` is ignored

## Nethereum.DevP2P — Admission, deadlines and capability negotiation

* `RlpxListener` takes a `DevP2PConfig.MaxPendingPeers` slot (default 50) before it accepts a socket, so no ECIES work runs beyond it, and holds the per-IP and per-subnet reservation for the life of an admitted peer. The per-IP cap `MaxInboundPerIP` does not apply to loopback, private and link-local addresses (`DevP2PConfig.IsLanAddress`, default `IpAddressExtensions.IsLan`); the per-subnet cap still does. A faulted admitted connection is disposed and frees its slots, and the accept loop backs off from 5 ms to 1 s on persistent errors
* Deadlines: `DevP2PConfig.HandshakeTimeoutMs` 5000, `StatusHandshakeTimeoutMs` 5000 (`RlpxConnection.ReceiveStatusAsync`, a whole-call deadline that ping and pong do not extend), `ReadTimeoutMs` 30000, `FrameWriteTimeoutMs` 20000. `ReceiveMessageAsync(TimeSpan frameReadTimeout, CancellationToken ct)` and `RlpxConnection.FrameReadTimeout` re-arm the read deadline for every frame, so a quiet peer that keeps pinging stays connected. A frame write that exceeds its deadline, or one the caller cancels after the frame began, disconnects and disposes the connection
* `CapabilityNegotiator.Negotiate` shares a capability only when its name and version are in both Hello lists and takes the highest such version. `DevP2PConfig.MaxEthVersion` (71) and `WithMaxEthVersion(int)` cap the advertised `eth` version, `AdvertiseSnap1` (`true`) controls `snap/1`
* `DialScheduler.TryReserveSlotAsync` claims the dial-history entry atomically and releases it when no slot is granted
* `NodeKeyStore.LoadOrCreate` writes the key file with mode `0600` from its first byte on Unix and removes a stale temporary file first; a failed `StaticPeerConnector.ConnectAsync` disposes its socket at once; `EnodeUrl.TryParse` returns `false` for a public key that is not hex

## Nethereum.DevP2P — Discovery

* discv4: `Discv4Listener` pings an unbonded sender back at once, with at most `MaxPendingPings` (1024) back-pings outstanding, and keeps at most `MaxBondedPeers` (8192) bonds, evicting table members first, then peers outside the table newest first, never the incoming bond. `RevalidateAsync(CancellationToken ct)` pings the least recently seen table entry every `RevalidationInterval` (10 s) and evicts it when no PONG arrives within `RevalidationTimeout` (2 s). NEIGHBORS replies are chunked at `Discv4NeighborsMessage.MaxNeighbors` (12) so each fits one datagram, and only a reply to a FINDNODE this node sent is harvested. `SendPingAsync` and `SendFindNodeAsync` take an optional `remoteNodeId`. `Discv4MessageEncoder.DecodeEnrRequestExpiration(byte[])` reads expirations as unsigned 64-bit, so an expiration above 2^63 is dropped as expired instead of throwing
* `Discv4RoutingTable` and `Discv5RoutingTable` admit at most `BucketIpLimit` (2) nodes per bucket and `TableIpLimit` (10) per table from one `IpLimitSubnetBits` (24) subnet and keep `MaxReplacements` (10) replacements per bucket (`ReplacementsFor`, `NextRevalidationCandidate`, `ReplacementsAtDistance`). The discv5 table honours the ENR sequence number and removes an entry after `MaxFailures` (3) failed walks (`RecordFailure`, `RecordSuccess`, `Remove`, `Entry.Failures`)
* discv5: every ENR in a NODES reply is signature-verified before it reaches the routing table or the dial queue; a NODES reply is accepted only for a pending FINDNODE (`Discv5RequestTracker.CompleteNodesChunk`, at most `MaxNodesEnrsPerRequest` 64 records in `MaxNodesChunksPerRequest` 16 chunks) and each record is checked for the requested distance, duplicates, a legitimate relay address (`IpAddressExtensions.IsValidRelayTarget`) and a UDP port above 1024. FINDNODE distances are bounded by `Discv5Listener.MaxLogDistance` (256) and de-duplicated, `MaxConcurrentTalkRequests` (1024) bound the TalkReq served at once, a failed handshake consumes its WHOAREYOU challenge on every error path, and inbound bans now expire after `BanDuration` (`DefaultBanDuration`, 5 minutes). `Discv5Listener.EnableInboundPacketFilter` (off by default) turns on the per-IP token bucket, so several nodes behind one address can handshake. `Discv5Listener.SessionManager` exposes the session manager
* `EnrTreeResolver` verifies each DNS child entry against its label hash and every ENR signature, rejects a high-S root signature, ignores a root with a lower sequence number than one already seen, bounds the walk to `MaxTreeDepth` (32) levels and a query budget, and survives a malformed link; `EnrTreeResolver(Action<string> log, Func<string, TimeSpan, CancellationToken, Task<List<string>>> queryTxt)` supplies the TXT lookup. `PeerDiscoveryService` skips nodes on special-purpose networks (`IpAddressExtensions.IsSpecialNetwork`), relayed addresses the sender could not name, and ports of 1024 or below
* `IpAddressExtensions.IsLan`, `IsSpecialNetwork`, `IsValidRelayTarget`, `RoutingIpLimits`, and `UdpClientExtensions.IgnoreIcmpConnectionReset(UdpClient)` (Windows: a reset from an unreachable peer no longer stalls the UDP read loops)

## Nethereum.DevP2P.Sync — Following the head

* Blocks reach a follower by pull. `BlockRangeAnnouncer` (`StartAsync()`, `Signal()`, `AnnounceIfDueAsync(ct)`, `AnnounceInterval`, `DefaultAnnounceInterval` 32, `DefaultPollInterval` 500 ms) sends `BlockRangeUpdate` through an `Eth68PeerPool` to every peer that negotiated `eth/69` or later, when the head moves `AnnounceInterval` blocks or moves back. `SyncPeerSession` validates each update with `BlockRangeValidator`, stores the peer head and raises `HeadAdvanced`; `PeerPoolManager.PeerHeadAdvanced` re-raises it. `PeerListenerOptions.OnBlockRangeUpdateReceived` receives the validated update. `NewBlock` and `NewBlockHashes` on `eth/69` and later, and `BlockRangeUpdate` on `eth/68`, disconnect the sender with `ProtocolBreach`
* `FollowingBlockSource(pull, pool, localHashAt, scheduler, maxRewindDepth, fallbackPoll)` wraps a pull source such as `DevP2PBlockSource`: it pulls again when a peer head advances (or after `DefaultFallbackPoll`, 1 s) and follows an announced head below its own only when the announcement is confirmed. A sibling at the height of the local head is pulled at once; a deeper one needs the announced header fetched by hash with the announced number and a parent the node holds, within `maxRewindDepth` (`DefaultMaxRewindDepth` 1024), so a forged announcement costs one block, not a re-download; a header no peer can serve quarantines the announcer, while a confirmed header on a deeper fork (its parent is not a block the node holds) is ignored without quarantining the announcer. The constructor without a scheduler follows only an announced head at most one block below the next block to pull, and never a deeper rewind. Head-advanced wake-ups coalesce into one pending signal
* `IFetchRequestScheduler.FetchAnnouncedHeadersAsync(startBlock, limit, ct)` prefers peers whose announced head covers the range, one at a time: a peer that answers empty is skipped, then every other peer is tried, and claimants that answered empty while another peer served are demoted for `FetchRequestScheduler.HeaderBatchQuarantineDuration` (2 minutes) and stay a last resort, so one peer announcing a far head cannot stall the tip
* `EthStatusValidator.Decode(int ethVersion, byte[] payload)` and `Violation(EthStatusExpectation expected, int negotiatedVersion, Eth68StatusMessage remote)` are the one Status rule for inbound, outbound and sequencer-client peers: network id, Status version against the negotiated version, genesis and the EIP-2124 fork id, in that order. `Decode` refuses an `eth/69+` block range whose earliest block is above its latest or whose latest hash is zero. `PeerListener` refuses a failing peer with `ProtocolBreach` before it is registered or served (with `MirrorRemoteStatus` only the version is checked); `PeerListenerOptions.ForkBlockNumbers` and `ForkTimestamps` carry the fork schedule. `EthStatusExpectation` and `DecodedEthStatus` are the argument and result types

## Nethereum.DevP2P.Sync — Holding peers to account

* A reply is served only when it delivers validated items. A zero-item reply earns no latency or success credit and does not reset the peer's timeout streak, the request goes to the next peer, and the peers that answered empty are demoted (ranked last, still usable as a last resort) only when a later peer in the same call served, so honest peers answering empty at the tip are never demoted. A partial reply is accepted. A `DevP2PBlockSource` pass that makes no progress ends its stream, and body and receipt requests honour the header quarantine
* Headers by number must be at most the requested count, start at the requested number and be contiguous in the requested direction; headers by hash must hash to the requested hash and chain from it (`BlockBatchValidator.ValidateHeadersByHashReply`). A violation throws `PeerMisbehaviourException` and quarantines the peer for headers. Header numbers are compared without narrowing, so a number above 2^64 is refused instead of wrapping
* `SyncPeerSession.GetReceiptsAsync(blockHashes, gasUsedByBlock, ct)` (and `IPeerRequestWorker.GetReceiptsAsync(peer, blockHashes, gasUsedByBlock, ct)`) bounds the receipts of an `eth/70+` block that arrives in pieces: more receipts than the header's gas used divided by 4500, or logs larger than the gas used divided by 8 bytes, abort the assembly with `PeerMisbehaviourException` and quarantine the peer
* `RelayMempool.SubmitAsync` does not announce a transaction that is already pending again
* snap/2 catch-up: a peer that times out, throws or returns undecodable block access lists twice in a row is excluded from the rest of the fetch round when another serviceable peer exists, so a silent peer costs at most two timeouts per window
* `IFetchRequestScheduler.RegisterTimeoutForQuarantine(peerId, kind, isTrusted, out triggeredAtCount)`, `RegisterSuccessForQuarantine(peerId, kind)` and `TimeoutStreakKind` (`Eth`, `Snap`) count peer failures once, in the scheduler quarantine; the backfiller no longer keeps its own counters
* The adaptive request timeout is capped at the configured `PerRequestTimeout`, so a timeout below 2 seconds no longer throws

## Nethereum.DevP2P.Sync — Serving peers

* `Eth68ServerSession` and `PeerListener` take an `InFlightDecodeLease` per message and release it as soon as the request is decoded, before the handler runs, so a slow-reading peer cannot pin the shared budget; `HandleEthMessageAsync(localId, payload, lease, ct)` and `Snap1Handler.HandleSnapMessageAsync(localId, payload, lease, ct)` take the lease
* A header, body, receipt or block-access-list request over its cap is clamped instead of disconnecting the peer, and the caps are 1024 each (`MaxHeadersPerRequest` was 192, `MaxReceiptsPerRequest` and `MaxBlockAccessListsPerRequest` were 256); a pooled-transactions request is no longer refused above 256 hashes, its reply is bounded by 2 MiB
* `StorageBackedEth68Handler` follows the skip and limit arithmetic of the protocol: a request for zero headers returns nothing, an overflowing skip or an origin above the signed 64-bit range returns only the origin or nothing, and a reverse skip past genesis stops. Bodies and receipts stop at the first unknown hash. An empty `Transactions` broadcast is accepted
* `PatriciaSnapRequestHandler.MaxStorageRangeAccountLookups` (2048) and `MaxTrieNodeTimeSpent` (5 s) bound a `GetStorageRanges` request, and an account without slots adds no list
* `PeerListenerOptions.IdleTimeout` (30 s, the per-frame read deadline) and `HandshakeTimeoutMs` (5000) default to the transport deadlines; snap is advertised only when it is served; a frame outside the negotiated `eth` capability disconnects the peer

## Nethereum.DevP2P.Sync — Transaction relay

* `MempoolAdmissionValidator` applies `TransactionAdmissionRules` (`Nethereum.CoreChain`) for size, gas limit, chain id, signature and fee caps; the blob cap is 1 MiB measured on the network form (`DefaultMaxBlobTransactionSizeBytes`), and blob count, sidecar and versioned-hash checks run as before
* `MempoolReorgReconciler.ReconcileAsync(bundle, commonAncestor, orphanedHead, orphanedBranchTransactions, winningBranchTransactions, ct)` takes the orphaned-branch transactions from the caller when it already holds them
* `RelayMempool` is leaf-only by default (`MempoolRelay.Ours`) and relays remote transactions only with `MempoolRelay.All`; a transaction already pending is not announced again

## Nethereum.DevP2P.Sync — Snap sync

Snap sync was reworked against failures seen while syncing a mainnet node, so a sync that is interrupted, outpaced by the chain or served by peers that lose the state still ends on a complete, certified state.

* The heal keeps one invariant: a trie node present at a path has a complete subtree for its hash. When the heal finds a stored node with the wrong hash it deletes it in the same round it schedules the refetch; it deletes stored nodes inside the path span of an extension it writes; it probes each sub-trie root it seeds; and an account leaf waits for both its code and its storage root. Before this, a storage trie rewritten and then reverted across two pivots could end the heal reporting a match over a trie that could not be walked. Phase 2 trie writers clear extension spans the same way when a run resumes over a previous run's nodes
* The heal phase ends on one root for the account trie and the storage heal, and finalize certifies and commits that root, never the rolling pivot. A guard checks that the stored root exists and hashes to it before certify. On a mainnet node the heal had converged 88 blocks before the rolling pivot, certify ran at the moved root, and the run took more than three hours to recover. A heal at a root no peer serves no longer deletes the stored root before it has fetched anything
* A sync starts no more than 64 blocks behind the verified tip, for `snap/1` and `snap/2`, and the pivot refresher does not move to a pivot that is itself stale; laid headers at the tip must hash to the verified tip. A mainnet node had anchored 16,000 blocks behind and streamed for 18 minutes against a root no peer served
* A hole that certify finds is repaired by deleting the stored ancestors of the missing node and healing at the current pivot, which fetches only the path down to it (about a dozen nodes for a hole deep in a 20,000-slot contract) instead of downloading the contract again. A large contract resumed after a kill is fetched again from its durable cursor, and the flat state is generated at finalize even when `EnableFlatReconcile` is off, because execution reads it
* One heal engine owns code, damage and re-pivoting: the seeded storage heal, the separate bytecode completion stage, the full-state bytecode scan and the post-sync compaction are gone, and the history backfill and receipt scrub stay idle while the follower is behind the tip
* Mismatched storage is healed at the live pivot instead of being recorded as deferred storage debt. A contract whose local storage root does not match the expected root, including a chunked one, is marked by `SnapTaskSet.MarkNeedHealIfRootMismatch`, and a storage-root mismatch is never an exception. `NeedsHealAccountsCodec` and `NeedsHealCodeCodec` (`Encode` / `Decode`) persist the accounts and code hashes the heal must visit, and the certify sweep hands holes it finds to the same heal
* An empty snap reply of any kind marks the peer stateless at that root, so it is not asked again for it; `IFetchRequestScheduler.ClearStatelessMarks()` clears the marks at bootstrap, re-heal and bytecode-pass entry, and a mark is dropped when its peer leaves the pool. A request for which every snap peer is stateless fails at once instead of retrying forever
* A heal with nothing it can fetch parks until a snap-capable peer joins or the pivot advances, and a joining peer wakes exactly one heal cycle at the same root; the heal-code, bytecode-sweep and flat-repair fetches wait for a peer instead of surfacing a bootstrap retry
* Finalize certifies the flat state with one reconcile run against the root the heal converged to, never the rolling pivot, whenever the bundle implements `IFlatStateReconciler` (`SnapBootstrapper.ReconcileAndCertifyFlatAsync(flatReconciler, stateRoot, pivotBlockNumber, logger, ct)`, `ReconcileFlatStateAsync(...)`); `EnableFlatReconcile` and `FinalizeVerify` are obsolete and ignored. `SnapBootstrapper.BuildStorageCompletenessGateReport(bundle)` reports pending heal accounts and damaged inventories (`SnapStorageCompletenessGateReport.CanFinalize`)
* `SnapSyncClient.SnapSyncCheckpoint.AccountsNeedingHeal` carries the needs-heal accounts in a Phase-2 checkpoint, and `SnapHashRanges.MinHash()` / `MaxHash()` are the zero origin and full-range limit of a snap request
* `SnapBootstrapper`, `SnapSyncOrchestrator`, `SnapSyncClient` and `TrieHealer` stay the public facades; the run is now composed of focused classes under `Snap/Bootstrap`, `Snap/Client` and `Snap/Healing` (pivot acquisition, `PivotWatch`, the history backfill, `Phase3Heal`, `FlatCertifier`, `ResumeRouter`, `Snap1Run`, `Snap2Run`)

## Nethereum.DevP2P.Sync — Phase-1 backfill

* A body hole goes back into the tip band with `TipBandBodyFollowService.RequeueFrom(fromBlock)` / `RequeueAndWaitAsync(fromBlock, ct)` (`IBodyFillCursor.Requeue`) instead of a second fetcher, and `BodyRepairer` is obsolete; saving a block body and its receipts has one owner, `BlockPersistence`
* Public additions: `BlockTaskQueue.EnqueueHeaderWithBody(header, hash, body)`, `ParallelBlockBackfiller.BackfillResult.ReceiptsUnmatched`, a public `TipBandBodyFollowService` constructor, a `ReceiptBackfillService` constructor that takes the `IPeerPool` and an `IPeerRequestWorker`, the `SyncPeerSession.AssembleReceipts70Async(int hashCount, Func<int, ulong, Task<(IReadOnlyList<List<Receipt>> entries, bool lastBlockIncomplete)>> fetchFromPos, int maxRounds, IReadOnlyList<ulong> gasUsedByBlock)` overload that bounds the assembled receipts by the gas used, and `PeerListenerOptions.DecodeLimiter` (`InFlightDecodeLimiter`)

## Bug Fixes

* One handshaken peer that answered every body request with nothing stalled the follower in a hot loop (610,727 requests in 8 s, the honest peer never asked); an empty reply now earns no credit and the next peer is asked
* A header reply with the wrong numbers, too many headers, or a number above 2^64 was accepted or wrapped; it is now a protocol violation that quarantines the peer
* `eth/70` receipts that a peer extended without limit were accepted; assembly is bounded by the block's gas used
* The listener admitted a peer of any network, genesis or fork; the Status rule is checked before the peer is registered
* Capability negotiation took the lower of two versions; a capability is shared only at a version both sides list
* An inbound peer that kept pinging but sent no `eth` or `snap` message was disconnected after 30 seconds, and a peer that pinged without sending Status held a slot for 30 seconds; the read deadline is per frame and the Status exchange has its own 5 s deadline
* A serving node disconnected a peer for an empty `Transactions` broadcast, for a header, receipt, block-access-list or pooled-transactions request over its cap, and mishandled an overflowing header skip, a reverse skip past genesis and a gap in a body or receipt request
* A `GetStorageRanges` request naming thousands of absent accounts walked the trie once per account without bound
* A snap/2 catch-up asked a silent peer again in every round at a cost of 60 s each
* A transaction already in the pool was announced again on every submission
* The adaptive request timeout threw `ArgumentException` for a `PerRequestTimeout` under 2 s
* discv4 never answered FINDNODE once the table held 15 nodes (the NEIGHBORS reply exceeded one datagram), never completed the endpoint proof for peers behind an address that had pinged recently, threw on an expiration above 2^63, and kept its bond and back-ping maps without limit
* discv5 accepted unsigned or unsolicited NODES records, banned an address for good, and kept a challenge alive after a failed handshake; a DNS ENR tree resolved records without checking child hashes or ENR signatures
* A Unix node key file was briefly world-readable while it was written, and a failed dial leaked its socket
* A snap run recorded mismatched storage as deferred debt that a later pass had to resolve, and certified the rolling pivot instead of the root the heal converged to; it could also cycle on a peer that had already answered empty at the same root
* A contract pulled across a pivot move recorded a debt that was then resolved one account at a time against a root no peer served any more, which took hours on mainnet; a direct peer's empty or non-hashing storage reply was recorded as debt instead of retried, because the default `ISnapPeer` overloads dropped the verifier
* A heal cycle that banked nothing at an unchanged root rebuilt itself every 2 seconds and asked again (2,045 empty cycles on a mainnet node while its consensus client was stuck); it now waits for a new pivot or a new snap peer
* A storage-root mismatch in Phase 2 threw and failed the whole attempt instead of marking the contract for heal
* In split storage, tip-band bodies were saved to the history store only, so blocks inside the hot window read back with no transactions
* A peer whose body or receipt requests failed synchronously spun the backfill at 100% CPU
* A peer could be counted, benched and dropped by two failure trackers at once; failures are counted once, by the scheduler quarantine
* The trusted-peer list was handed to the peer pool as one joined string, so a trusted peer that dropped was never dialled again (4,444 attempts over 18 hours on a mainnet node); when the pool was full the dial loop also discarded the candidates behind the first
* A body whose withdrawals the validator rejected was accepted by the block task queue, an enode with a `discport` suffix could not be dialled, and a removed peer kept its snap-state bench

## Breaking Changes

* Removed, with `BlockRangeAnnouncer` and `FollowingBlockSource` as the replacement (blocks propagate by announcing the head and pulling): `IBlockPublisher` (`BroadcastNewBlockAsync`, `ConnectedPeerCount`), `DevP2PBlockPublisher`, `PushedBlockSource` (constructor, `Name`, `PendingCount`, `OnNewBlock` x2, `LastChainBreak`, `StreamAsync`, `GetHealthAsync`, `ReportBadBundleAsync`) and `CatchUpThenFollowBlockSource` (constructor, `CaughtUp`, `LastChainBreak`, `StreamAsync`, `GetHealthAsync`, `ReportBadBundleAsync`). Wrap the pull source (`DevP2PBlockSource`) in `FollowingBlockSource`; announce the head with `BlockRangeAnnouncer`
* Removed: the `NewBlockReceived` events of `SyncPeerSession`, `Eth68ServerSession` and `DevP2PSequencerRpcClient`; use `SyncPeerSession.HeadAdvanced` or `PeerPoolManager.PeerHeadAdvanced`
* Removed: `PeerListenerOptions.OnNewBlockReceived` (`Action<NewBlockMessage>`); use `OnBlockRangeUpdateReceived` (`Action<BlockRangeUpdateMessage>`)
* Removed: `Eth68ServerSession.MaxPooledTransactionsPerRequest`; a pooled-transactions request is no longer refused above 256 hashes
* Signature: `Discv4Listener.SendPingAsync` and `SendFindNodeAsync` gained an optional trailing `byte[] remoteNodeId`, and `Discv5RequestTracker.RegisterFindNode` gained optional `requestedDistances` and `senderAddress`. Source stays compatible; a caller compiled against 7.0 must be rebuilt
* Constant values: `RlpxFrameReader.MaxDecompressedFrameSize` 32 MiB to 16 MiB - 1; `Eth68ServerSession.MaxHeadersPerRequest` 192 to 1024, `MaxReceiptsPerRequest` and `MaxBlockAccessListsPerRequest` 256 to 1024; `MempoolAdmissionValidator.DefaultMaxBlobTransactionSizeBytes` and the default of its `maxBlobTransactionSizeBytes` parameter 917,504 to 1,048,576. Rebuild callers that read these constants
* Behaviour: `DevP2PConfig.HandshakeTimeoutMs` and `PeerListenerOptions.HandshakeTimeoutMs` default to 5000 (were 10000) and `PeerListenerOptions.IdleTimeout` to 30 s (was 2 minutes); set them explicitly to keep the old values
* Behaviour: `CapabilityNegotiator.Negotiate` shares a capability only at a version both sides list (7.0 used the lower of the two); a peer that offers only versions this node does not advertise shares nothing for that protocol
* Behaviour: `NewBlock` and `NewBlockHashes` on `eth/69+`, `BlockRangeUpdate` on `eth/68`, a frame outside the negotiated capabilities, an `eth` or `snap` message over 10 MiB, a response that matches no pending request, and a Hello with a mismatched node id, more than 64 capabilities or a client id over 256 characters disconnect the peer; a Status for another network, genesis or fork id is refused; a decoded frame over 16 MiB - 1 is refused
* Behaviour: `DevP2PSequencerRpcClient` advertises only `eth/68` (`DevP2PConfig.WithMaxEthVersion(68)`; 7.0 advertised `eth/68` to `eth/71`) and bounds its header, body and receipt replies with `RlpxResponseBound.Items`
* Behaviour: the per-IP discv5 packet filter is off unless `Discv5Listener.EnableInboundPacketFilter` is set; discv5 inbound bans expire
* Behaviour: `ISnapPeer`'s default verifying overloads (`GetAccountRangeAsync`, `GetStorageRangesAsync`, `GetByteCodesAsync` with a `verifyResponse` delegate) throw `FetchRequestFailedException` when the delegate returns `false` (7.0 ignored the delegate)
* Behaviour: `IFetchRequestScheduler` (`FetchAnnouncedHeadersAsync`, `ClearStatelessMarks`, `RegisterTimeoutForQuarantine`, `RegisterSuccessForQuarantine`), `IPeerRequestWorker.GetReceiptsAsync` (gas-used overload) and `IBodyFillCursor.Requeue` are added as default interface members, so existing implementations still compile and keep their old behaviour
* Obsolete, not removed (the flat state is always certified and nothing is deferred): `SnapSyncOrchestratorOptions` / `SnapRunOptions` `EnableFlatReconcile` and `FinalizeVerify` (ignored); `DeferredHealAccountsCodec` and `DeferredHealCodeCodec` (use `NeedsHealAccountsCodec` and `NeedsHealCodeCodec`); the deferred-debt members of `SnapBootstrapper` (`HasDeferredStorageHealWork`, `ResolveOpenDebtFinalRootsWithRetargetAsync`, `EnsureBytecodeCompleteAsync`, `FetchMissingBytecodeAsync`, the `finalizeVerify` overloads of `ReconcileAndCertifyFlatAsync` and `ReconcileFlatStateAsync`, the debt counters of `SnapStorageCompletenessGateReport`), `SnapPhase2State.DeferredStorageDebts` and `SnapshotDeferredStorageDebts()`, the `DeferredStorageDebtFinalRootResolver` methods `ResolveAsync`, `BuildFinalStorageSeeds`, `MarkFinalStorageSeedsDeepComplete` and `EnsureDebtRowsForDeferredHealAccounts`, and `SnapTaskSet.CompleteOwnerViaLocalRoot`; `SnapSyncClient.SnapSyncCheckpoint.DeferredStorageDebts`; `BodyRepairer` (use `TipBandBodyFollowService.RequeueAndWaitAsync`); `PeerFailureTracker` and the peer-penalty constants of `ParallelBlockBackfiller` (the scheduler quarantine counts failures); the `ReceiptBackfillService` constructor without an `IPeerPool`
