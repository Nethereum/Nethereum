# Chain Hosting — Nethereum 7.0

Nethereum 7.0 adds the node-hosting layer that turns the storage-and-execution engine and the devp2p/snap sync engine into runnable nodes. One shared composition library, `Nethereum.ChainNode.Hosting`, wires storage, mempool, peer serving and the sync stack into a single `ChainNode` object from one `ChainNodeConfig` — so the mainnet follower, the AppChain server and the DevChain all compose from the same building blocks instead of hand-assembling `PeerPoolManager`, `PeerListener` and `RelayMempool` each. On top of it, `Nethereum.MainnetChain` composes a read-only mainnet follower — snap-bootstrap, block validation against the CoreChain executor, an optional beacon light-client consensus gate, and `eth_*`/`net_*`/`web3_*` JSON-RPC serving — packaged as an embeddable library and as the `nethereum-mainnetchain` dotnet tool (`Nethereum.MainnetChain.Server`). The pre-existing `Nethereum.DevChain` / `Nethereum.DevChain.Server` are reworked onto the shared hosting layer and gain a JWT-authenticated **Engine API** endpoint, so a Nethereum dev chain now produces payloads for — and validates payloads from — a consensus client or a second node over `engine_*`. `Nethereum.ChainNode.Hosting`, `Nethereum.MainnetChain` and `Nethereum.MainnetChain.Server` are net-new for 7.0; `Nethereum.DevChain` and `Nethereum.DevChain.Server` existed at 6.1.0 and were reworked in-range. `Nethereum.MainnetChain` and `Nethereum.MainnetChain.Server` ship as `7.0.0-preview`, so their interfaces may still move; `Nethereum.ChainNode.Hosting`, `Nethereum.DevChain` and `Nethereum.DevChain.Server` ship as `7.0.0`. Every capability below is exercised by a passing test.

## Nethereum.ChainNode.Hosting — Shared Node Composition

New package: the composition root every Nethereum-hosted chain shares. Hand it an `IChainDefinition` (genesis + `IChainProfile` + tip source) and a `ChainNodeConfig` and it opens storage, builds the mempool, starts inbound serving and the sync stack, and gives you back one running `ChainNode`. RPC serving and peer discovery (discv4/discv5/DNS) stay the host's job.

* One node object from one config — `ChainNode.StartAsync(definition, config, loggerFactory)` is `ComposeAsync` + `StartServingAsync` + `StartSyncAsync` in one call, exposing `Bundle` (`IChainStoreBundle`), `Mempool` (`ChainNodeMempool`), `Listener` (`PeerListener`, null when `Network.Serve` is false), and `Sync` (`ChainNodeSyncStack`, null when `Sync.Mode` is `None`)
* Three-stage composition when you need to wire in between — `ChainNode.ComposeAsync` (with an optional `storageFactory` seam), then `StartServingAsync(ChainNodeServeCallbacks)`, then `StartSyncAsync(minPeerLatestBlockFactory:)`; both start-stages no-op when their config gates them off and are idempotent
* Coherent presets — `ChainNodeConfigFactory.Create(ChainNodePreset)` (`InMemory`/`Pruned`/`Archive`/`SnapSync`/`SnapSyncV2`) sets `Storage` and `Sync.Mode` together (and `Sync.Snap.AdvertiseSnap2` for `SnapSyncV2`), and refuses an unknown preset rather than returning a default; `AsRole(ChainNodeRole)` sets the mempool retention/relay policy per role (`Signer`→Full/Ours, `Follower`→RelayOnly/Ours, `GossipNode`→Full/All)
* The mempool as one unit — `ChainNodeMempool.Create(...)` bundles the `TxPool` (`ITxPool`), the `Relay` (`RelayMempool`), the `BroadcastPool` (`Eth68PeerPool`), and the `TrustedAdmission`/`TrustedAdmissionFrom` seams that admit a trusted peer's pushed transactions without normal gossip admission
* Storage composed from config — `ChainNodeStorage.Open(...)` maps `ChainNodeStorageConfig` onto `RocksDbStorageOptions` (path-keyed state, node history + index, split hot/cold history, geth-style freezer, log index) or opens the in-memory bundle, and refuses illegal combinations at open time (e.g. freezer history without a signer)
* Serving and sync stacks as reusable pieces — `ChainNodeServeListener.StartAsync` builds the inbound eth/snap `PeerListener` from `ChainNodeNetworkConfig` (serving its own real status by default, not the mirrored peer status), and `ChainNodeSyncStack.StartAsync` builds the peer pool, scheduler and block source, honouring the trust/dial asymmetry between `TrustedPeers` (dial + trust), `TrustedBootnodes` (outbound trust-if-dialed only) and `TrustedNodeIds` (inbound trust only)
* One authoritative config surface — `ChainNodeConfigSurface` marks every `ChainNodeConfig` leaf `Live`/`Disabled`/`NotYetWired` for each host and drives their `--help-advanced`; a reflection-based coverage test fails the build if a field is added without a descriptor entry or a `Live` field without a resolvable consumer
* Shared maintenance and lifecycle — `ChainNodeMaintenanceRunner` runs the pre-boot maintenance ops (wipe-state, compact-all, rebuild-from-flat, verify-flat) and sets the process exit code before normal startup; `TrustedTransactionAdmission`, `ChainHeadResolver` and `DefaultChainProfile` round out the surface

## Nethereum.MainnetChain — Mainnet Follower Library

New package: a read-only Ethereum mainnet follower and serving node, embeddable in a .NET host. It cold-starts from a snapshot via snap sync, validates every block through the CoreChain executor stack, keeps a local state database, and serves that state back over JSON-RPC and (optionally) to other devp2p peers. It follows and serves; it does not propose or mine.

* Register the whole follower graph — `AddMainnetChainServer(this IServiceCollection, MainnetChainServerConfig)` (and the `WebApplicationBuilder` overload) wires validation, the consensus gate, the node factory, the RPC dispatcher and the hosted services; `MapMainnetChainEndpoints` maps `POST /` (JSON-RPC single + batch) and `GET /` (health)
* Production vs test composition — `MainnetNodeComposition.AddMainnetNodeAsync` opens RocksDB and loads genesis up front (awaited before `Build()`), registering the store bundle plus the DevP2P peer pool, scheduler and block source; `UseInMemoryBundleAndSource(IBlockSource)` swaps in an in-memory bundle and a scripted source for tests
* The follower node itself — `MainnetChainNodeFactory` builds the `FollowerChainNode` wired with the mainnet fork registry (real KZG/BLS precompile backends) and the proof-of-work reward policy, wrapped in the configured `IConsensusBlockGate`; `MainnetChainNodeAccessor` is the singleton holder so the RPC surface reads off the same node the follower loop drives
* Optional beacon light-client consensus gate — with a beacon endpoint, `LightClientConsensusBlockGate` (`IConsensusBlockGate`) rejects any block whose hash disagrees with the beacon-attested chain and accepts blocks beyond the light-client cursor (graceful degradation); without one the gate is CoreChain's `AlwaysAcceptConsensusBlockGate`
* Trusted canonical tip / snap pivot — `LightClientCanonicalSource` (`ICanonicalStateRootSource`) tracks the attested head so the snap pivot stays inside peers' snapshot window; `AddMainnetChainServer` composes it with CoreChain's `MainnetKnownCheckpoints` into a `CompositeCanonicalStateRootSource` when a light client is present, and falls back to checkpoints-only (latest returns null) when it is not
* Finality labels — `LightClientFinalityCursorProvider` (`IFinalityCursorProvider`) resolves `finalized`/`safe` RPC block tags to the light-client's trusted heights, falling back to `latest` before the light client bootstraps
* Hosted services — `MainnetChainHostedService` runs the optional snap-bootstrap then the block-follower loop; `LightClientHostedService` keeps the beacon light client updated on its cadence; `SnapSyncProgressReporter` emits the periodic phase/peer/staleness heartbeat; `SnapBootstrapInvoker` drives the shared snap orchestrator with the mainnet fork activations, finishing with a flat-state reconcile and verify (`SnapEnableFlatReconcile` / `SnapFinalizeVerify`, both on by default). The invoker leaves `SnapSyncOrchestratorOptions.BalHealEnabled` at its default `false`, so mainnet snap sync runs snap/1; the snap/2 bootstrap in `Nethereum.DevP2P.Sync` is not enabled on mainnet
* Progress reporting that tells a busy disk from a stalled sync — while the store's write valve (`IStateWriteBackpressure`) is closed, `SnapSyncProgressReporter` logs `Syncing: state download paused — storage backpressure: …` with the pressure, and after ten minutes without progress it logs a `snap.state.paused` Warning naming that pressure; the peer-blaming `snap.state.stalled` error fires only when the valve is open. The reporter's constructor takes an optional `TimeProvider` for its clock
* Fork identity is derived, not declared — `MainnetChainProfile` / `MainnetChainDefinition` report mainnet's genesis hash, network id and fork thresholds from the shared mainnet schedule, and build a handshake worker that advertises mainnet's live-head fork-id
* Startup safety — `ConsensusStartupGuard` refuses to start a mainnet follower with no beacon endpoint unless unverified consensus is explicitly allowed, rather than silently trusting whatever peers serve; `HistoryBackfillMode` selects when the block-archive receipt/body backfill runs

## Nethereum.MainnetChain.Server — The Mainnet Follower Executable

New package: the `nethereum-mainnetchain` dotnet tool. It runs the follower with snap sync on by default, validates every block as it follows the head, and serves JSON-RPC on `http://127.0.0.1:8545`, resuming where it left off on restart.

* Consensus-first by default — the server refuses to start without a `--beacon` endpoint (a forgotten flag fails loudly instead of trusting peers), and `--allow-unverified-consensus` is the explicit, discouraged opt-out
* Flat CLI over the library config — `--port`/`--host`/`--data-dir`/`--trusted-peer`/`--listen-port` map onto `MainnetChainServerConfig`, with `--no-snap`, `--metrics-port` (Prometheus text on a separate port), and layered `appsettings.json` `MainnetChain` section / `MainnetChain__` env vars / `--MainnetChain:*` expert overrides surfaced via `--help-advanced`
* One-shot maintenance ops — `--wipe-state` (clear state, keep the block archive and cursors), `--rebuild-state-from-flat`, `--verify-flat` (+ `--verify-flat-sample N`), each running before normal startup and setting the exit code
* Stable node identity — persists a raw 32-byte node key at `<data-dir>/nodekey` (override with `--node-key-file`) reused for inbound and outbound, so the enode survives restarts and a peer's `admin_addTrustedPeer` sticks
* Storage/tuning knobs — `--flush-cadence`, `--checkpoint-every`, `--cache-size` (plain or suffixed sizes), history-backfill mode, path-keyed state by default
* Embeddable — the same three-call host (`AddMainnetChainServer` + `MapMainnetChainEndpoints` + `Run`) hosts the follower inside any ASP.NET Core app

## Nethereum.DevChain — Local Dev Chain, Reworked onto Shared Hosting

Existed at 6.1.0; reworked for 7.0. A local Ethereum-compatible chain with full EVM execution through Amsterdam, instant/interval auto-mining, forking, and Hardhat/Anvil-compatible RPC — now composing on `Nethereum.ChainNode.Hosting` and gaining a JWT-authenticated Engine API.

* Engine API endpoint — `AddEngineApiServer(EngineApiServerConfig)` stands up a second, JWT-guarded port that serves CoreChain's `engine_*` handlers (`AddEngineHandlers`) behind `EngineApiHost`; `EngineJwtValidator` enforces the HS256 / fresh-`iat` / 60-second-window rules and `EngineJwtSecret` loads the shared secret — so a Nethereum dev chain can be driven by a consensus client, or by a second Nethereum node, over the standard Engine API. The endpoint is off by default and enabled through configuration only (`DevChainServerConfig.EngineApiEnabled`, with `EngineJwtSecretPath`, `EnginePort` and `EngineBindAddress`; there is no CLI flag)
* Produce-and-adopt over the Engine API — one node builds payloads (`engine_forkchoiceUpdatedV3`/`V4` with payload attributes → `engine_getPayloadV3`/`V4`/`V6`) and a second node adopts them (`engine_newPayloadV3`/`V4`/`V5` → `engine_forkchoiceUpdatedV3`/`V4`), reconstructing the producer's chain; `engine_exchangeCapabilities` and `engine_getClientVersionV1` are served too; unknown-parent payloads report `SYNCING` and a payload that fails validation (for example a mismatched `gasUsed`) reports `INVALID`
* Mempool-style nonce admission over RPC — `eth_sendRawTransaction` rejects a nonce below the sender's next nonce (`nonce too low: have X, want Y`) and queues a future-nonce transaction, returning its hash; block production still only includes a transaction whose nonce is next
* Composes on the shared stack — `DevChainComposition` builds a `DevChainComposedNode` from the same `ChainNodeMempool.Create` / `ChainNodeServeListener` / `ChainNodeSyncStack` building blocks `ChainNode` uses, over its own `DevChainNode` bundle and `DevChainDefinition`, so serving is gated on `Network.Serve` and sync on `Sync.Mode`
* RocksDB storage mode — `DevChainStorageBackend` resolves the storage mode (SQLite default, in-memory, or `--rocksdb` path-keyed RocksDB "same as mainnet") into a `DevChainChainStoreBundle`, releasing the RocksDB lock cleanly on stop so the directory can be reopened
* Rewind the chain head — `debug_setHead` (`DebugSetHeadHandler`, backed by `DevChainNode.SetHeadAsync`) rewinds the dev chain to an earlier block: blocks, transactions, receipts and state above it are removed and `eth_blockNumber` reports the new head. Rewinding to block 0 resets accounts and storage to the genesis snapshot; any other target rewinds through the historical-state journal and needs a journaling `HistoricalStateStore` (otherwise `NotSupportedException`). As in geth, a target at or above the current head is refused ("not allowed to rewind to a future block"). `SetHeadAsync` is on `DevChainNode` only; `IDevChainNode` is unchanged
* One DevChain RPC registry — `DevRpcHandlerExtensions.CreateDevChainRegistry()` assembles the DevChain RPC surface (standard, dev and Anvil-alias handlers, the dev `eth_accounts` override and the Hardhat impersonation handlers) in one place, and `AddDevChainServer` uses it; `AddDevHandlers` now also registers `debug_setHead`
* Discovery refused, not silently inert — `DevChainServerConfigValidator` throws if discv4/discv5 is enabled on a dev chain (a dev chain has no discovery), rather than accepting a flag that does nothing
* Unchanged dev-chain surface — `DevChainNode` (`ChainNodeBase`, `IDevChainNode`), instant/interval mining, snapshots/revert, fork-from-live, blob sidecars, `evm_*`/`hardhat_*`/`anvil_*` RPC, and geth-compatible `debug_traceTransaction`/`debug_traceCall` remain

## Nethereum.DevChain.Server — The DevChain Executable

Existed at 6.1.0; updated for 7.0. The `nethereum-devchain` dotnet tool — a local development node with a JSON-RPC server, comparable to Hardhat Network or Anvil, EVM opcodes through Amsterdam.

* Storage-mode flags — `--in-memory`, `--persist [DIR]`, and the new `--rocksdb` (+ `--data-dir`) path-keyed RocksDB mode "same as mainnet", alongside the default auto-cleanup SQLite
* Standard dev-node surface — pre-funded HD-wallet accounts (Hardhat/Anvil default mnemonic + derivation path), auto-mine or `--block-time` intervals, `--fork`/`--fork-block` from a live network, `--hardfork` selection (default amsterdam), the `eth_*`/`evm_*`/`hardhat_*`/`anvil_*` RPC set, and the EIP-4844 beacon blob-sidecar endpoint
* Layered config — `appsettings.json` `DevChain` section binds `DevChainServerConfig`; `AddDevChainServer` + `MapDevChainEndpointsAsync` embed the whole server in any ASP.NET Core host, and the same hosting extensions back the Aspire DevChain variant
