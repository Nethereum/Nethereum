# Consensus — Nethereum 7.0

Nethereum 7.0 turns the consensus-layer libraries into a working, trust-minimised beacon-chain client and a production Clique proof-of-authority engine. You can now bootstrap an Ethereum light client from a weak-subjectivity checkpoint and follow the beacon chain to its finalized and optimistic heads — verifying every sync-committee BLS aggregate signature and selecting the right signing domain and container shape per fork from Phase 0 through Fulu — then read a cryptographically-trusted execution header out of it. The consensus SSZ containers that carry that data are now fully fork-parameterised: a single `ConsensusFork` value drives the field set, merkleization gindices and proof depths of every `LightClient*` and `ExecutionPayloadHeader` container, with a `ChainSpec` slot→fork schedule that picks the fork automatically. On the execution-side, `Nethereum.Consensus.Clique` gained a consensus-admission gate that refuses any block whose seal is not an authorised signer *before* it executes, plus a pluggable validator-vote store — so a Clique follower cannot be fed a chain anyone could write. None of the six packages here is new since 6.1.0; every one below is an existing package extended in place (the SSZ *primitive* library `Nethereum.Ssz`, the beacon REST client `Nethereum.Beaconchain` and `Nethereum.ChainStateVerification` included). The consensus-layer containers here are `Nethereum.Consensus.Ssz`, distinct from `Nethereum.Model.SSZ` (the execution-block SSZ encoders written up in the Foundations release note).

## Nethereum.Consensus.LightClient — Trustless Beacon Chain Light Client

The Ethereum light-client sync protocol implemented over minimal trust: bootstrap from a trusted finalized checkpoint, then track finalized and optimistic heads by verifying 512-validator sync-committee BLS aggregate signatures — no full node, no execution client. Point it at a beacon REST endpoint and it maintains a verified head you can read execution headers and (with `Nethereum.ChainStateVerification`) proof-checked account state from.

* Orchestration — `LightClientService(ILightClientApi, IBls, LightClientConfig, ILightClientStore)` with `InitializeAsync` (bootstrap from the configured `WeakSubjectivityRoot`, or derive one from the beacon node's latest finality update when none is set) and the three drive methods `UpdateAsync` (finalized head + sync-committee rotation), `UpdateFinalityAsync` and `UpdateOptimisticAsync`; `LastRejectReason` records why the most recent update was refused
* Sync-committee signature verification per period — an update's `SyncAggregate` is checked against the committee for the *signature slot's* period (the store's current committee at the store period, the next committee at period + 1), with the signing domain derived internally per fork from the signature slot, so the client does not freeze at a committee-period boundary by verifying a next-period signature against the current committee
* Provenanced block-hash history — `LightClientState` keeps the last 256 execution block hashes as `ProvenancedBlockHash` (a `readonly struct` carrying a `BlockHashFinality` of `Optimistic`/`Finalized`), so a finalized entry cannot be silently overwritten by a conflicting optimistic write (`SetBlockHash` throws on a finalized-vs-finalized conflict)
* Trusted execution headers with staleness detection — `TrustedHeaderProvider` (`ITrustedHeaderProvider`) exposes `GetLatestFinalized`/`GetLatestOptimistic` as a `TrustedExecutionHeader`, raising `StaleHeaderDetected` (or throwing `StaleHeaderException` when `ThrowOnStaleHeader`) past a configurable age threshold
* Purpose-built persistence — `LightClientStateCodec.Encode` / `TryDecode` serialise `LightClientState` (SSZ containers plus a `ProvenancedBlockHash`-valued dictionary that reflection-based serializers do not round-trip) as a `Magic("LCST")+Version+length+payload+CRC32` frame, fork-aware per container, returning `false` (never throwing) on a truncated or CRC-mismatched buffer; `ILightClientStore` with `InMemoryLightClientStore` is the storage seam
* Validating configuration and per-network constants — `LightClientConfig` (32-byte-validated `GenesisValidatorsRoot`/`WeakSubjectivityRoot`, `ChainSpec` defaulting to `ChainSpec.Mainnet`) and `LightClientNetworks` with the baked-in per-network `genesis_validators_root` (`TryGetGenesisValidatorsRoot(BigInteger chainId, out byte[])`, `CreateConfig(BigInteger chainId, byte[] weakSubjectivityRoot = null)` for mainnet/Sepolia/Holesky)

## Nethereum.Consensus.Ssz — Fork-Aware Consensus SSZ Containers

The consensus-layer SSZ containers for light-client sync, reworked so one `ConsensusFork` value drives every container's field set, merkleization gindices and proof depths across the fork schedule — the data model the light client and beacon REST client above are built on. (This is the consensus-layer SSZ package; the execution-block SSZ encoders in `Nethereum.Model.SSZ` are a separate package, covered in the Foundations release note.)

* Fork axis — `ConsensusFork` (chronological enum `Phase0`…`Gloas`, so `fork >= ConsensusFork.Capella` is spec-meaningful) and `LightClientForkSpec`, the per-fork constants and predicates the containers use internally: `HasExecutionPayloadHeader`, `HasWithdrawalsRoot`, `HasBlobGasFields`, `ExecutionBranchDepth`, `FinalityBranchLength`, `CurrentSyncCommitteeBranchLength`/`NextSyncCommitteeBranchLength` and their gindices — widening the finality and sync-committee branches at Electra
* Slot→fork schedule — `ChainSpec` (with the `ForkActivation` value struct validating a 4-byte fork version) resolving `GetForkAtSlot(ulong)` and `GetForkVersionAtSlot(ulong)`, `SlotsPerEpoch`/`SecondsPerSlot`, and the prebuilt `ChainSpec.Mainnet` mapping each mainnet fork to its version (Electra `0x05000000`, Fulu `0x06000000`), refusing an unscheduled Gloas rather than guessing
* Fork-parameterised light-client containers — `LightClientBootstrap`, `LightClientUpdate`, `LightClientFinalityUpdate`, `LightClientOptimisticUpdate` and `LightClientHeader`, each with `Encode()`/`Encode(ConsensusFork)`/`Decode(byte[], ConsensusFork)`/`HashTreeRoot(...)` so a header round-trips under exactly the field set and branch lengths its fork defines
* The consensus primitives — `BeaconBlockHeader` (112-byte fixed), `SyncCommittee` (512 pubkeys + aggregate), `SyncAggregate` (participation bits + BLS signature) and the fork-shaped `ExecutionPayloadHeader` (Capella `WithdrawalsRoot`, Deneb `BlobGasUsed`/`ExcessBlobGas`), plus `SszBasicTypes` constants
* Strict wire decoding — the containers reject a wrongly-sized or over-/under-long buffer rather than tolerating it, validated against the Ethereum consensus-spec test vectors across forks

## Nethereum.Consensus.Clique — PoA Engine, Consensus Gate & Validator Voting

The EIP-225 Clique proof-of-authority engine, extended for 7.0 with the seam that makes a Clique *follower* safe and a persistent validator-vote store. The engine (turn-based scheduling, ECDSA seal, snapshot state, epoch signer commits) already shipped; the new work is admission control and voting.

* Consensus-admission gate — `CliqueConsensusBlockGate` implements CoreChain's `IConsensusBlockGate`, refusing a block whose recovered seal is not an authorised signer *before* execution (`IsBlockCanonicalAsync` → `ConsensusBlockGateResult.Reject`) and applying the block to snapshot state on import (`OnBlockImportedAsync`), so a follower that imports without this check cannot be fed a chain anyone could write (EIP-225 puts the seal in `extraData` precisely so it can be verified against the authorised set)
* Pluggable validator voting — `ICliqueProposalStore` with `InMemoryCliqueProposalStore` (`SetProposal(target, authorize)`, `Discard(target)`, `Proposals`), address-normalised and lock-guarded, so add/remove-signer intents are held outside the engine and cast into produced blocks by `CliqueBlockProductionStrategy`
* Turn-based production and validation — `CliqueEngine.IsInTurn`/`GetDifficulty`/`CanProduceBlock`/`GetSigningDelayAsync`, `SignBlock`/`RecoverSigner`, and `ValidateBlockInternal(header, parent)` returning a `CliqueValidationResult` (recovered signer or error) that both the gate and the strategy consume
* Snapshot state — `CliqueSnapshot` (authorised `Signers`, active `Votes`, `VoteTally`, majority `RequiredVotes`) cloned for thread-safety and committed to `extraData` at epoch boundaries, enforcing the EIP-225 recent-signer limit and the epoch-checkpoint signer-list ordering

## Nethereum.Beaconchain — Beacon REST Client & Light-Client Mapping

The .NET beacon-chain REST client, extended so its light-client responses map cleanly into the fork-aware `Nethereum.Consensus.Ssz` domain model the light client verifies.

* Light-client REST surface — `BeaconApiClient` (`IBeaconApiClient`) with the `LightClient` sub-client (`ILightClientApi`) for bootstrap, updates, finality and optimistic endpoints, and `StateForkResponse` for beacon-state fork data
* Fork-stamped response mapping — `LightClientResponseMapper.ToDomain(...)` maps each light-client response DTO to its `Nethereum.Consensus.Ssz` container (`LightClientBootstrap`/`LightClientUpdate`/`LightClientFinalityUpdate`/`LightClientOptimisticUpdate`), stamping the `ConsensusFork` derived from the response so the container decodes and merkleizes under the correct fork
* Blob sidecars — `IBeaconApiClient.GetBlobSidecarsAsync(blockId = "head", indices = null)` and `BlobSidecarHelper` (`ExtractBlobs`, `ToBlobSidecar`) fetch and decode a block's EIP-4844 blob sidecars into `Nethereum.Model.BlobSidecar`

## Nethereum.Ssz — Strict Merkle-Branch Verification

A small hardening of the SSZ primitive library the consensus containers build on.

* `SszMerkleizer.VerifyProof(leaf, branch, depth, index, root)` now rejects a branch whose element count differs from `depth` (was a `< depth` lower-bound check, now an exact `!= depth` match), matching the consensus-spec `is_valid_merkle_branch` where the `Vector[Bytes32, depth]` type enforces an exact length

## Nethereum.ChainStateVerification — Verified State on the EVM State Seam

* **Breaking:** `VerifiedNodeDataService` now implements the EVM `IStateReader` instead of `INodeDataService` — results are `EvmUInt256`, `GetTransactionCount` became `GetTransactionCountAsync`, and `AccountExistsAsync` was added — so proof-verified state plugs directly into the EVM
* The verified-state interceptor returns `eth_getStorageAt` results as a fixed-width 32-byte word, and proofs are checked through the unified `ProofVerification` entry point
