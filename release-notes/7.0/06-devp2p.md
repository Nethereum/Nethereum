# DevP2P & Sync — Nethereum 7.0

Nethereum 7.0 adds native devp2p networking and snap/BAL sync. Nethereum can now join the Ethereum wire network directly — dial and accept real peers, discover them, and sync a chain from scratch — with no go-ethereum or other external client in the loop. It ships as two new packages: `Nethereum.DevP2P` (transport + discovery) and `Nethereum.DevP2P.Sync` (the sync engine, fronted by a single `SyncNode` object — the `Web3` of networking).

## Nethereum.DevP2P — RLPx Transport & Peer Discovery

New package that speaks the Ethereum wire protocol directly in .NET. You can now open authenticated RLPx sessions with real peers, discover them across three protocols, and control who you dial and who you accept.

* RLPx transport — ECIES handshake, AES-CTR + Keccak-MAC framing, and capability negotiation across `eth/68`–`eth/71` and `snap/1` (`snap/2` opt-in), with each protocol's message-id offset computed so multiplexed sub-protocols never collide (`CapabilityNegotiator.Negotiate`)
* discv4 discovery — Kademlia over signed UDP with EIP-868 endpoint-proof bonding
* discv5 discovery — WHOAREYOU/HKDF authenticated sessions with TalkReq/TalkResp
* EIP-1459 DNS discovery — ENR-tree resolution
* Outbound dial scheduling — bounded concurrency, inbound/outbound ratio, recent-dial suppression, trusted-peer bypass
* Inbound admission — `NetRestrict` CIDR allow-list, per-IP/per-subnet caps, post-handshake `MaxPeers`
* Persistent peer cache that carries dial history across restarts

## Nethereum.DevP2P.Sync — Snap-First Sync Engine

New package that syncs a chain over the network from scratch, fronted by one `SyncNode` facade. You can now cold-start a node straight to live state, run a full archive sync, serve other peers, and relay your own transactions — all in-process.

* `SyncNode` — a single facade over the peer pool, fetch scheduler, inbound listener, and mempool relay
* EIP-2124 fork-ID computed and validated on every peer handshake, rejecting incompatible peers the way geth does
* Full (archive) sync — Phase-1 parallel backfill of headers, bodies, and receipts, each content-addressed against the header's commitments and parent-hash validated, so a malicious peer cannot poison the archive
* Snap sync — Phase-2 streams accounts, storage, and bytecode over `snap/1`, verifying every range against its Merkle-Patricia proof; Phase-3 heals any still-missing nodes by walking the trie until the computed root matches the pivot
* Rolling pivot — the pivot advances with the chain during a long sync, so you finish on a fresh head instead of one that is already stale
* Resumable — a checkpointed `SnapSyncState` blob resumes a killed sync in the phase it stopped, mid-heal included
* Flat-state certification — verified storage pages, including large contracts streamed in chunks, are written to the flat (execution-read) state as they arrive, and before go-live the flat state is verified (`SnapSyncOrchestratorOptions.FinalizeVerify`, on by default) and optionally reconciled against the trie (`EnableFlatReconcile`, which the mainnet follower turns on); flat rows still buffered for SST ingest are flushed before that reconcile, so they are certified with the rest. Known limitation: the reconcile (`FlatStateReconciler`) walks and decodes every trie node and runs before go-live, so on mainnet it holds the node out of Phase 4 for hours — a single pass took about 4.5 hours on the test host. Unlike go-ethereum, which regenerates its snapshot in the background while the node follows the chain, 7.0 does not start following until the reconcile completes
* Storage completes inside the sync — a large contract's storage subtask that no peer can serve is reverted and retried after a short backoff instead of being abandoned, so the contract completes in Phase 2; a contract whose storage pages came from different roots across pivot moves is repaired by the Phase-3 trie heal, which fetches only the nodes that changed, instead of by re-downloading its whole storage. Flat slots left over from the older roots are removed by the final flat reconcile, so a library host that does not use the mainnet follower should turn on `EnableFlatReconcile` (off by default)
* Storage backpressure is waited out, not restarted — when the store's write valve (`IStateWriteBackpressure`) pauses Phase 2, the stream consumers wait, cancellably, until it releases instead of recycling the attempt, and a pivot move while they are paused still re-anchors the sync at the new root. The pause log line reports how long the stream has been paused and escalates from Information to Warning after ten minutes, and `SnapSyncMetrics` publishes the same duration as the `snap.phase2.backpressure.paused_for` gauge (`Phase2BackpressurePausedFor`)
* Large contracts count as progress — each page applied to a large contract's cursored storage subtask adds to the synced-slot and synced-byte counters (`snap.phase2.storage_slots.synced`, `snap.phase2.storage_bytes.synced`) and can trigger a checkpoint, as account ranges do, so when one large contract is the only work left the checkpointed counters keep moving and the liveness supervisor does not time out (`SnapSyncClient.TaskSetStallTimeout`) and restart Phase 2. Before a checkpoint promotes a large contract's resume cursor it commits that contract's open trie nodes (`ResumableStorageScope.CommitDirtyNodes`), so a restart never resumes past slots that were not written. A write stall on the trie store's memtable flush does not fail Phase 2: the checkpoint and the Phase-2 finalise log `snap.phase2.flush_skipped` and carry on
* Serving & relay — serves `eth` and `snap/1` to inbound peers and relays locally-submitted transactions; the default relay policy (`MempoolRelay.Ours`) makes a node a leaf that never re-gossips remote transactions, while `MempoolRelay.All` opts a node in to onward gossip
* Snap/2 bootstrap (EIP-8189; preview, off by default via `SnapSyncOrchestratorOptions.BalHealEnabled`) — when the option is on, the run is not `BackfillOnly`, and the boot pivot is Amsterdam or later, `SnapBootstrapper.RunAsync` takes a separate snap/2 path modelled on go-ethereum's `syncv2`; otherwise it runs the snap/1 sync described above. Turning it on needs a RocksDB-backed bundle (`RocksDbChainStoreBundle` is the `IFlatStateTrieGenerator`; the in-memory bundle is not), the scheduler and peer pool the `SyncNode` supplies, and header follow (`SnapSyncOrchestratorOptions.HeaderFollow` or the orchestrator's own); a missing one throws `InvalidOperationException` before any state is touched. Phase 2 downloads flat state only: every account and storage page is still range-proof verified, large contracts are still fetched as cursored subtasks, and no trie node is written. When the pivot moves mid-flight, the attempt is drained and checkpointed, then the flat state is rolled forward block by block with each intervening block's Block Access List — headers are read from the local canonical chain in windows of 512 and must chain from the old pivot, each BAL is fetched over `snap/2` and checked against its header's BAL hash, flat rows beyond the durable download frontier are pruned first, and the pivot is persisted after every block — before Phase 2 re-enters at the new root, including across repeated moves. A resumed download catches up the same way before Phase 2 continues
* Snap/2 trie generation — after Phase 2 the node persists the `SnapPhase.Generating` phase, generates the state trie from the flat state (`IFlatStateTrieGenerator.GenerateTrieFromFlatAsync`) and checks it against the pivot's state root, then fetches any bytecode Phase 2 deferred and commits the pivot. Phase 2, the catch-up and generation send no `GetTrieNodes` request. A root mismatch throws naming both roots and leaves the phase at `Generating`, and a restart in that phase regenerates against the same pivot without downloading again. Generation has not yet been measured on a mainnet-sized state
* Snap/2 resume and reset rules — a saved `Generating` state whose pivot is still canonical, or a saved `Phase2Running` state whose pivot is canonical, Amsterdam and has tasks, is resumed; any other saved state is wiped and the run starts fresh (`snap.bootstrap.snap2_reset reason=phase|not_canonical|pre_amsterdam|no_tasks`). A catch-up whose applied pivot is no longer canonical, whose target is not ahead of it, or whose gap is above 90,000 blocks also wipes the snap state (`snap.bal_catchup.reset_required reason=pivot_reorged|pivot_not_ahead|gap_exceeds_bal_retention`). With the option on, a resume waits (`snap.bootstrap.pivot_wait`) instead of adopting a pivot below its saved one while the locally laid headers lag the tip. Snap/2 is not enabled on mainnet: the mainnet follower's `SnapBootstrapInvoker` does not set `BalHealEnabled`, so mainnet snap sync runs snap/1

Interop is exercised by a manual harness against go-ethereum's `devp2p` tool and a live mainnet bootnode (run locally with a user-provided geth build; not CI-gated).
