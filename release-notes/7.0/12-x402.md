# X402 Payments — Nethereum 7.0

Nethereum 7.0 rebuilds `Nethereum.X402` — the HTTP-402 "pay-per-request" stack — onto **x402 protocol version 2**, and interop-verifies it against the coinbase/x402 reference implementation in both directions. You can now protect an ASP.NET Core endpoint with a single line, have a client detect the 402, sign a gasless stablecoin authorization off-chain, and settle it on-chain — over the default **EIP-3009** `transferWithAuthorization`/`receiveWithAuthorization` path or the new **Permit2** asset-transfer method (any ERC-20, no EIP-3009 support required in the token). The package already existed at 6.1.0 as a v1 implementation; 7.0 is a v2 migration plus a net-new Permit2 method and a full security-hardening pass, not a new package. Every capability below is exercised by a passing hermetic, in-process DevChain, or opt-in mainnet-fork test.

## Protocol v2 wire format

The whole stack moved to x402 v2 shapes and headers, matched field-by-field against the reference spec.

- `x402Version = 2` throughout; `amount` (was `maxAmountRequired`); networks are CAIP-2 (`eip155:<chainId>`), parsed/formatted by `Caip2` (`Caip2.FormatEip155`, `Caip2.TryParseEip155ChainId`)
- New models: `PaymentRequired` (top-level `Resource` + `Accepts` + `Extensions`), `ResourceInfo` (`{Url, Description, MimeType}`), `ExactSchemeExtra` (`{AssetTransferMethod, Name, Version}`); `PaymentPayload` carries the chosen requirement in its `Accepted` field
- Three base64 headers: `PAYMENT-REQUIRED` (402 response), `PAYMENT-SIGNATURE` (request), `PAYMENT-RESPONSE` (200 response)
- v2 error vocabulary in `X402ErrorCodes`, matching the reference reason strings

Traceability: `Models/X402V2InteropTests.cs:69,91,115` (reference JSON deserializes into our models; our models serialize to reference keys), `Blockchain/Caip2Tests.cs:10,20`, `Models/PaymentRequiredTests.cs`, `Models/PaymentPayloadTests.cs`, `Models/PaymentRequirementsTests.cs`.

## Client — X402HttpClient

An `HttpClient` wrapper that runs the 402 flow (detect → select → sign → retry) and derives its EIP-712 signing domain from the `PaymentRequirements` the server returns — the client is not pre-configured with a token or chain.

- Automatic and manual flows; all verbs (`GetAsync`/`PostAsync`/`PutAsync`/`DeleteAsync`/`SendAsync`); `X402HttpClientOptions.MaxAmount` (required, atomic units) caps the automatic flow and throws `X402PaymentExceedsMaximumException` before signing
- Emits the correct payload for the selected requirement's method — EIP-3009 by default, or a Permit2 payload when `extra.assetTransferMethod == "permit2"`
- `PaymentPolicy` allow-list (`AllowedNetworks`/`AllowedAssets`/`AllowedRecipients`, each empty = unrestricted) refuses a redirected/asset-swapped/wrong-chain 402 with `X402PaymentPolicyViolationException` (carrying a `PaymentPolicyDimension`) **before anything is signed**
- Response helpers (`HasPaymentResponse`, `GetTransactionHash`, `GetPayerAddress`, `IsPaymentSuccessful`) read the `PAYMENT-RESPONSE` header; `DefaultPaymentRequirementsSelector` picks the requirement to pay

Traceability: `Client/X402HttpClientAutomaticFlowTests.cs:640,679,715` (recipient/asset policy refusal before signing + allow-listed happy path), `Client/X402HttpClientPermit2Tests.cs:26` (client permit2 payload recovers to payer), `Integration/X402EndToEndTests.cs:107` (full client→server→facilitator→settle on the in-process DevChain).

## Server — X402Middleware & replay protection

`app.UseX402(...)` protects routes with per-route `RoutePaymentConfig` requirements; on a matching request with no `PAYMENT-SIGNATURE` it emits 402 with `PaymentRequired`, otherwise it verifies and settles before forwarding.

- Route matching + 402 emission with the accepted requirements in both the `PAYMENT-REQUIRED` header and body
- Serve-before-settle replay protection: `X402Middleware` reserves the payment identity (`PaymentReplayIdentity` = payer + nonce) via `IPaymentReplayStore` **before** running the endpoint, rejecting a replay with `invalid_exact_evm_nonce_already_used`; on by default (`X402Options.EnablePaymentReplayProtection`, `PaymentReplayRetention`)
- Default `InMemoryPaymentReplayStore` (single-instance, TTL-swept); register a distributed `IPaymentReplayStore` for scaled deployments

Traceability: `AspNetCore/X402MiddlewareTests.cs:20,41` (402 + `PAYMENT-REQUIRED` header), `Integration/X402MiddlewareReplayTests.cs:42,60,75` (replay rejected without re-running the endpoint; distinct payments both run; disabled path re-runs), `Server/RoutePaymentConfigTests.cs:11`.

## EIP-3009 payment processors

The default "exact" scheme, settled with EIP-3009 gasless authorizations. Two variants share `ExactScheme3009ServiceBase` and `PaymentAuthorizationValidator`, differing only in recipient binding, recovery domain, and the on-chain call submitted.

- `X402TransferWithAuthorisation3009Service` — facilitator submits `transferWithAuthorization`
- `X402ReceiveWithAuthorisation3009Service` — receiver submits `receiveWithAuthorization` (binds authorization `To` = receiver)
- Verify binds the signed authorization to the route requirement (recipient = `PayTo`, value = `Amount`, token, network) before trusting it, then checks signature, balance, nonce and time window
- Authorization building/signing: `TransferWithAuthorisationBuilder` / `ReceiveWithAuthorisationBuilder` (over `Eip3009AuthorisationBuilderBase`) and `TransferWithAuthorisationSigner` (`SignWithPrivateKeyAsync` / `SignWithWeb3Async` for external signers), domain derived from the requirement

Traceability: `Blockchain/X402TransferE2ETests.cs:79` (verifies and settles on the in-process DevChain via `MockUSDCDeployment`), `Blockchain/X402ReceiveE2ETests.cs:79` (verify path — the mock token has `transferWithAuthorization` but not `receiveWithAuthorization`, so receive settle is not covered in CI), `Blockchain/X402TransferWithAuthorisation3009ServiceTests.cs`, `Blockchain/X402ReceiveWithAuthorisation3009ServiceTests.cs`, `Signers/TransferWithAuthorisationSignerTests.cs:25,48`, `Signers/TransferWithAuthorisationBuilderTests.cs`.

## Permit2 asset-transfer method (net-new)

A second "exact"-scheme asset-transfer method that works with any ERC-20 the payer has approved to the canonical Permit2 contract — no EIP-3009 support needed in the token. The payer signs a Permit2 `PermitWitnessTransferFrom` naming the **x402ExactPermit2Proxy** as spender and the route recipient as the witness; the facilitator settles via `proxy.settle`, which pins the destination.

- `X402ExactPermit2Service` — verify binds spender = proxy, witness `to` = `PayTo`, exact amount and token, deadline/`validAfter` window, EIP-712 signer recovery, and the on-chain prerequisites (proxy deployed, payer balance, Permit2 allowance); settles via `x402ExactPermit2Proxy.settle`
- `X402ExactSchemeProcessor` — dispatcher routing to Permit2 when the payload carries a `Permit2Authorization`, else EIP-3009; merges supported kinds. Registered with `AddX402ExactProcessor`
- `Permit2WitnessSigner` signs/recovers the witness typed data; `Permit2SchemePayload` is the wire model; `Permit2AuthorizationMapper` bridges wire ↔ domain; the proxy-settle surface is the generated `SettleFunction` (`[Function("settle")]`) plus the `X402Permit2Addresses`, `Witness` and `PermitWitnessTransferFrom` structs
- Settle-revert decoding: `Permit2SettlementErrorMapper` identifies the Permit2 custom error via the code-generated error collection (`Permit2Service.FindCustomError`) and maps it to a specific reason (e.g. `InvalidNonce` → `invalid_exact_evm_nonce_already_used`, `SignatureExpired` → `permit2_deadline_expired`, `InsufficientAllowance` → `permit2_allowance_required`) at the pre-settle simulation, with best-effort transaction replay for a mined revert

The underlying Permit2 EIP-712 signing types and the `Permit2Service` contract handler were relocated out of `Nethereum.Uniswap` into `Nethereum.ABI` / `Nethereum.Contracts` / `Nethereum.Signer.EIP712` and shipped as first-class primitives (`web3.Eth.GetPermit2Service()`) — see the Foundations and RPC/Web3 release notes. X402 **consumes** those; it does not re-implement them.

Traceability (hermetic): `Permit2/Permit2WitnessSignerTests.cs:18` (sign round-trips to signer), `Permit2/Permit2SettlementErrorMapperTests.cs:30,38,44` (custom-error → code mapping, built from each error's ABI selector, no chain), `Client/X402HttpClientPermit2Tests.cs:26`.
Traceability (opt-in mainnet fork, non-CI — see Interoperability): `Permit2/X402Permit2ProcessorForkTests.cs:34,61,82,110,128,144,161` (verify+settle over the wire, dispatcher routing, real-nonce replay decode, recipient/amount/allowance rejections, ERC-1271 wallet), `Permit2/X402Permit2ForkTests.cs`.

## Facilitator

A facilitator verifies and settles payments on behalf of resource servers, so a server needs no blockchain infrastructure. It runs as a REST service — standalone, or mounted in the resource server's own ASP.NET Core app — and `UseX402` reaches it over HTTP through `HttpFacilitatorClient`.

- `IX402PaymentProcessor` — `VerifyPaymentAsync` / `SettlePaymentAsync` / `GetSupportedAsync`; processors take a facilitator key (or `IAccount`) and a `Dictionary<int, IClient>` per chain id
- DI on-ramps: `AddX402TransferProcessor` (EIP-3009) and `AddX402ReceiveProcessor` (receiver-submitted) each take a private-key string, an `IAccount`, or an `IServiceProvider` account factory; `AddX402ExactProcessor` (EIP-3009 + Permit2 dispatcher) takes the same three forms
- Standalone host: `AddX402FacilitatorControllers` exposes `FacilitatorController` (`POST /facilitator/verify`, `POST /facilitator/settle`, `GET /facilitator/supported`)
- Client and middleware proxy: `HttpFacilitatorClient` (`IFacilitatorClient`) and `X402FacilitatorProxyProcessor` route verify/settle to a remote facilitator; middleware never trusts the client-supplied `Accepted`, always binding to the route's requirement

Traceability: `Facilitator/FacilitatorControllerTests.cs:28` (verify returns success), `Facilitator/HttpFacilitatorClientTests.cs:11`, `Facilitator/FacilitatorIntegrationTests.cs`.

## Security hardening

An adversarial security review drove a hardening pass:

- Client allow-list + fail-closed `MaxAmount` (above) so a malicious server cannot redirect, asset-swap, or switch chains under the cap
- Pre-settle `eth_estimateGas` simulation on both facilitator paths → `invalid_exact_evm_transaction_simulation_failed` instead of burning gas on a doomed transfer (paused/blocklisting/fee-on-transfer tokens)
- ERC-1271 smart-wallet signature fallback (`Erc1271SignatureVerifier`): when ECDSA recovery ≠ payer and the payer holds code, `isValidSignature` (magic `0x1626ba7e`) is consulted
- Serve-before-settle replay reservation (above); optional `ILogger` on the facilitators (swallowed verify/settle exceptions logged; `JsonException` → coded error, never reflected to the caller); bounded response buffering

Traceability: `Integration/X402MiddlewareReplayTests.cs:42`, `Permit2/Permit2SettlementErrorMapperTests.cs:30`; (opt-in fork) `Permit2/X402Erc1271SmartWalletForkTests.cs:26,85` (accepts a valid ERC-1271 wallet signature, rejects the wrong signer), `Permit2/X402Permit2ProcessorForkTests.cs:82` (simulation/replay decode).

## Reference demo apps

Three runnable sample apps under `src/demos/` (source-only reference apps, not NuGet packages), all updated to the v2 API this cycle:

- **`Nethereum.X402.SimpleServer`** — a minimal ASP.NET Core resource server: `app.UseX402(...)` with a `/premium` (EIP-3009) and a `/premium-permit2` route (`RoutePaymentConfig` + `PaymentRequirements` with `ExactSchemeExtra`), plus a free endpoint, pointed at the hosted `x402.org` facilitator.
- **`Nethereum.X402.SimpleClient`** — a console client showing both flows against `SimpleServer`: the automatic `X402HttpClient` path (detect 402 → sign → retry, then read the `PAYMENT-RESPONSE` settlement via the extension helpers) and a manual path that parses `PaymentRequired`, selects a requirement, and pays it explicitly.
- **`Nethereum.X402.FacilitatorServer`** — a standalone facilitator REST service: `AddX402ExactProcessor(account, rpcEndpointsByChainId)` (EIP-3009 + Permit2 dispatcher) + `AddX402FacilitatorControllers`, RPC endpoints per chain id from configuration, Swagger UI.
